## Versioned deliverable template

Store stable ID/version, internal and client descriptions, eligible service/intent relationships, prerequisites, incompatible selections, preparer/reviewer capability requirements, document class, required inputs, proposed time/ROM inputs with provenance, scope limitations, completion criteria, release policy reference, effective dates, source and activation status.

For each actual deliverable store account/project and approved-scope-version links, responsible preparer, assigned reviewer, due date, status, document-version links, completion evidence and release references. Preparing a deliverable and releasing it are distinct actions. A new file revision must not inherit a previous revision's technical approval or release approval.

Development default: professional outputs require designated qualified review and an explicit release action to a permitted audience. Implement configurable review policies; final role assignments and class-specific exceptions remain recorded owner decisions. Proposed report structures may use synthetic content, clearly distinguished from real technical conclusions.

## Dependencies and acceptance

- A deliverable can be traced to authorized scope and its promised due date/output; an unapproved add-on remains proposed.
- A report draft stays private even when its project is client-visible. Permission, exact-version approval and release checks apply to direct file access and packages.
- Project status distinguishes field completion, deliverable preparation, technical review, release and delivery.
- Document-linked questions retain the exact document version, project, scope and responsible reviewer context.
- Replacement/supersession preserves history and applies the current historical-access policy. Retention/holds are handled by Documents and Audit.
- Tests exercise a completed authorized output, a missing prerequisite, a rejected review, a revised file after approval, unauthorized access and a package with a restricted child document.
