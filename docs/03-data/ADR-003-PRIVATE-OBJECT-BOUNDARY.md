# ADR-003: private ingest objects, quarantine and the future version boundary

Date: 2026-10-08. Status: **proposed engineering contract for development; architecture only**. Scope: the next bounded private-object part of SEC-001C, supporting C01/C07 and M19, with compatibility constraints from C02/M13 and M12. Input commit: `283882ced0f8e7be119f4b3c4c75a3f913572bde`. No storage implementation, provider configuration, real-file inspection, scan effectiveness, cloud application, API acceptance or owner business approval is established by this document.

## 1. Decision and dependency boundary

Implement a small **private ingest-object substrate**, independent of `document_versions`: an immutable-byte manifest, exact internal object grants, append-only scan observations and human clearance decisions, plus a narrow authenticated gateway. All new files start quarantined. Only explicitly granted synthetic internal actors may inspect them through that gateway; no client deliverable or general document portal opens in this slice. Ordinary direct Storage access stays denied. No signed download or signed upload URLs are issued.

The dependency order is directory/access foundation + accepted audit foundation → private ingest objects → DOC-001 immutable versions/reviews/releases. SEC-001C must not query a nonexistent `document_versions` table or depend on DOC-001, which already depends on SEC-001. The lead should represent these as bounded child tasks, not remove DOC-001's substantive acceptance requirements to satisfy the parent.

`public.documents` remains the existing logical document identity. Preserve its rows, UUIDs, `version_label`, `release_state`, links and seed bytes. These legacy labels confer **no** file, release, review or audience authority. Do not backfill file manifests or released versions from labels without actual bytes and verified provenance. An ingest object is neither a document version nor a released document; clearance means only eligible for the next explicitly authorized internal handling step.

The smallest useful first implementation is the database contract and denial policies below, with deterministic synthetic state/permission tests. Then implement the bounded gateway and real local/provider tests. Do not add projects, a general job framework, document packages, thumbnails, OCR, AI, a release UI, external notifications or a Moldo adapter to make this substrate work. M12 queues can later consume its truthful pending/error/review status; an uploaded file cannot advance a project to delivered or closed.

## 2. Source facts and non-goals

The pinned foundation contains seven public tables, including logical `documents`, but no file-object or immutable version relation. The directory migration adds `account_access` and `account_capability_grants`; its only allowed capabilities are `view_account` and the two `view_asset` scopes. Its helper rejects unknown capability keys. Legacy roles, including `system_admin` and `document_controller`, do not authorize storage. Private-object capability support therefore needs an additive constraint/helper change, not a new policy that assumes such grants already exist.

The separately pinned audit migration is an accepted input, not present at this worktree's source commit and not cloud-applied. Its checked event families currently cover only profiles, account access and capability grants. Its only system key is `database_privileged_operation`; service-role writes are not human acts. Its audit ACLs prevent direct client and service-role insertion. A new storage event cannot be emitted until a reviewed additive event/writer extension exists. Preserve the accepted migration unchanged.

The observed repository target is the existing `auxiliumos-dev` (`txofqxictwecgcnvezlb`). Earlier read-only observations of an empty backend and PostgreSQL 17.6.1.127 are not a fresh provider preflight. This task made no target changes. The current local PGlite harness models PostgreSQL 18.3 with simulated Auth and no genuine Storage service. It cannot prove hosted Auth, object serving, scan behavior or target-version parity.

No PHI v1 remains decided. Real uploads stay disabled until OD-013's incident contact and handling procedure are recorded and the technical gates below pass. OD-011 leaves permanent destruction and client audit exports disabled. Qualified humans retain technical, release, signature and commercial authority. Moldo stays independent; its staff/managers receive no OS profile, membership or grant from integration identity. No Moldo database, bucket or essential record is touched. Companion redesign remains deferred.

## 3. Small additive data contract

Use application-owned relations in the existing non-exposed `private` schema. Enable RLS, deny base-table access to `PUBLIC`, `anon` and `authenticated`, explicitly control table/column/function privileges, and expose only reviewed typed RPC wrappers. Deny direct base-table writes to `service_role` too; grant only the server routines actually needed. A BYPASSRLS role still requires table privileges. Do not add application tables/functions to provider-owned `storage` or `auth` schemas.

| Addition | Required contract |

Transport fields: checked `upload_state`, server `upload_attempt_id`, reservation expiry, state revision, bounded failure code. Finalized evidence: verified SHA-256, verified byte size, detected media type, verification time. Security controls: scan state `pending/running/result`, server `current_scan_attempt_id`, current scan/clearance references, bounded `quarantine_reason_code`, independent `visibility_restricted`, `preservation_hold`, and one-way `ingest_closed_at`. Unique active object/subject/capability. Grants are explicit trusted fixture provisioning in this slice, not inferred from uploader, role, account read, technical administration or scan ownership. |

All object/scan/decision/grant references enforce same-account composite keys. A clearance's selected observation must also belong to the **same object and digest**, enforced by composite unique/FK constraints or checked locked transitions, not merely independent FKs to valid UUIDs. A current scan or clearance pointer has the same requirement. The required facility must match `(facilities.id, facilities.account_id)`; mismatched tenants fail even for privileged routine calls. Account/facility/creator/key are immutable from reservation onward. No cascade deletes erase objects, decisions, grants or audit history. Index the membership/active-grant lookups and referencing object/account/facility/scan keys; use partial uniqueness for active grants. Review indexes against the actual query plans rather than inventing a scale claim.

Do not mutate the original foundation migration. Generate the implementation migration using the installed CLI after `--help` discovery, order it after the accepted audit migration, and keep that exact migration filename in the lead's task allocation. Schema/RPC naming and bucket layout are delegated engineering choices, not new owner blockers.

The first fixture surface accepts only small synthetic UTF-8 `text/plain` payloads, capped at 64 KiB in both gateway and bucket configuration. This is an engineering bound for a reproducible test, **not** an approved product-format limit, retention period, scientific threshold or service commitment. Production is disabled by trusted server configuration, never by a caller-supplied `is_demo` flag. General PDFs/images/video and account-level non-facility documents require a subsequent bounded extension.

## 4. Effective authorization and least privilege

Every user action re-evaluates: validated Supabase bearer subject → linked active demo profile → active demo membership for the object's account → current `view_account` and appropriate `view_asset` facility entitlement → the action's explicit current grant → permitted object/security state. Reuse ADR-002's subject/directory checks; never authorize from user-editable metadata, a role label, stale JWT membership claims, email or an external Moldo identity.

| Action | Additional predicate |
| --- | --- |
| Reserve/upload/finalize | Current exact facility `ingest_private_object` capability; caller is the reservation's original uploader for upload/finalize; matching unexpired attempt and permissible transport state. Owning an upload gives no inspection or release permission. |
| Status | Original uploader with current ingest entitlement, or an exact applicable object grant; current account/facility access still required. Return bounded status/next-action codes, not content, filenames, raw paths, other actors' grants or unfiltered counts. |
| Normal internal inspection | Exact `inspect_cleared_object`; finalized bytes; current matching malware-pass observation and human `cleared_no_phi` decision; no visibility restriction; ingest not closed. |
| Quarantine inspection | Exact `inspect_quarantined_object`; finalized bytes; current malware-pass observation; ingest not closed. This dedicated, audited incident-review route may inspect a suspected-PHI/awaiting-human object despite normal-visibility restriction, but never a malware-blocked/unscanned/error object. It is not an alternate generic download route. Live access requires the designated incident-review authority/procedure under OD-013. |
| Human clearance | Exact `clear_object`; same current active identity/membership/facility checks; current matching malware-pass observation; compare expected object state revision and digest. Record the qualified designated human's security disposition, not a scanner/service/AI assertion. Inspection and clearance grants do not imply each other. |
| Report suspected PHI | Current original-uploader ingest entitlement or an exact inspection/clearance grant, plus current account/facility access. This can only narrow access: invalidate clearance, record suspicion and restrict normal inspection. It cannot clear, release or destroy an object. |
| Holds/restrictions/grant provisioning | Explicitly enumerated trusted synthetic provisioning routines only in this slice, with audit and expected-revision checks. No browser administration or live authority assignment is added. |

Base rows, scans and grants are not generally discoverable through the Data API. A missing or forbidden ID returns the same safe outward `not_found_or_unavailable` response after authentication; do not reveal whether another tenant has it. An invalid token is unauthenticated. Validation, conflict and temporary backend errors are distinct safe outcomes. RLS-filtered reads may be empty, so do not require HTTP 403 for every denial.

Private owner-controlled helpers may use `SECURITY DEFINER` only where necessary to cross the denied base-table boundary. Pin `search_path=''`, qualify names, use no dynamic SQL, accept no actor/profile parameter, validate every capability/scope/state, revoke default execution, and explicitly grant only the intended wrapper/role. Public wrappers should be minimal `SECURITY INVOKER` delegates. The private schema remains unexposed; possession of an RPC name is not authorization. User-mutation routines require the accepted authenticator/authenticated gateway provenance checks in addition to action authorization. Service-only routines use a separate fixed technical provenance path; they may not manufacture a human clearance.

For finalization/clearance and other consequential transitions, use short database transactions with expected revision and row locks. Lock the subject, membership, relevant grants and object in a documented consistent order; re-read their state under those locks. A concurrent revocation either precedes and denies the mutation or follows its committed authorization. Test actual concurrent sessions on the target engine. Do not hold these locks while uploading, scanning or calling the Storage API.

## 5. Private bucket and gateway boundary

Create one bucket, proposed ID `os-private-ingest`, explicitly `public=false`, with the synthetic restrictions above through the supported Storage API. Keep quarantine and clearance in authoritative database state rather than copying a file between buckets to imply release. An example server-generated key is `<account-uuid>/<facility-uuid>/<object-uuid>/payload`; no original filename, patient/client text or caller-chosen path enters it. Bucket and full key must resolve from the manifest; prefixes and unguessable UUIDs are organization/defense in depth, not permission.

For this bucket, ordinary `anon` and `authenticated` Storage operations are all denied: upload, authenticated/public download, HEAD/info, list/search, move/copy, overwrite/upsert, delete, signed-download creation, signed-upload creation, transforms, resumable and S3 variants. No application route issues a signing token. Use scoped restrictive policies as defense in depth where supported, with no ordinary permissive policy for this bucket. Inspect **all** existing policies: a newly added permissive `false` policy does not cancel another permissive allow. Do not globally revoke provider-owned schema privileges, drop unrelated policies or depend on inaccessible managed-schema modifications. Verify exposed schemas and every supported route on the actual provider. An existing bucket with unexplained objects/configuration or prior signing routes must be reconciled before reuse; do not claim that these policies revoke a previously issued valid signing capability. A privileged actor can still mint an out-of-band bearer link, which is outside the ordinary-client guarantee and requires operational control.

The gateway alone uses the configured backend Storage credential to put/get exact manifest-owned keys. Use separate per-request user-JWT and backend-Storage clients; never reuse mutable Authorization headers across users. Authenticate with `auth.getUser(token)` against the intended project, then forward that user's bearer token to the user-context database RPC for authoritative permission/state checks. Do not call `getSession()` or decode claims and treat them as verified authority. A server `service_role` query cannot substitute for this user-context check.

Service credentials bypass Storage RLS. Therefore the chosen boundary protects ordinary clients, **not** a compromised backend key/operator. A key is not magically bucket-scoped because code uses one bucket. Keep it outside source/browser/logs; restrict deployment/operator access; expose no arbitrary path/URL/proxy endpoint; reject tenant/key/MIME/actor overrides; use provider APIs only. Treat independent scoped credentials as a future hardening option only after provider support and the whole route are verified. This slice does not promise provider-level WORM storage or immutability against a database/storage administrator.

Supabase `owner_id` is provider metadata, not the OS account owner or an entitlement. Service-key uploads may have no owner. The manifest's account/facility/creator facts are authoritative; neither null owner nor uploader equality permits a read. Use `owner_id`, not deprecated `owner`, if recording observed provider metadata. Do not forge ownership to impersonate the user.

Read Storage metadata if needed, but perform object upload/copy/move/delete through the Storage API, never by changing `storage.objects` rows. SQL metadata deletion is not byte deletion. No delete, overwrite, move or copy action is exposed by this slice, including via the gateway. A changed byte sequence needs a new object UUID/key. No object-key reuse after expiry/abandonment.

## 6. Bounded API and upload consistency

One modular gateway can serve the following operations; no frontend route is required for the first backend acceptance. Wire names are proposals, not existing APIs. All bodies use explicit allowlists; extra actor, path, release or authority fields fail validation.

| Operation | Inputs and result |
| --- | --- |
| `POST /private-objects` | `{accountId, facilityId, byteSize, mediaType}` plus idempotency UUID. Typed user RPC allocates one reservation and immutable server key, with server expiry. Return `{objectId, state, expiresAt, stateRevision}` and an application upload route, never a Storage bearer URL. Same actor/key/request returns the original reservation; same key/different immutable request yields conflict. |
| `PUT /private-objects/{id}/bytes` | Authenticated bounded bytes, exact reserved content type/length. Recheck uploader entitlement; atomically claim one attempt/revision before provider I/O. Put with `upsert:false`. Return stored-unverified or retryable failure honestly, never finalized/released from an SDK success alone. |
| `POST /private-objects/{id}/finalize` | `{expectedStateRevision}`. A trusted verifier reads back the exact provider object, checks existence/size/type and computes SHA-256 from bytes. The database accepts evidence only from the restricted verifier routine; a client's digest or provider ETag is not verified SHA-256. Recheck the uploader's current grant in the final commit. Return finalized-and-quarantined status, not visible/released. |
| `GET /private-objects/{id}` | Authorized safe status: transport state, quarantine/review state, revision, bounded failure/next-action codes; no signed URL or raw scan output. Unknown counts are not zero. |
| `GET /private-objects/{id}/content` | Internal cleared-inspection path only. Check authorization before provider fetch and again immediately before response; compare the bounded fetched bytes' SHA-256/length to immutable finalized evidence and deny on mismatch; append authorization audit before any response bytes. Return exact verified bytes as an attachment, `Cache-Control: private, no-store`, `X-Content-Type-Options: nosniff`, safe generated filename. No redirect, CDN/public cache, inline active content, range/resume or content transformation in this bounded slice. |
| `GET /private-objects/{id}/quarantine-content` | The separate authorized malware-pass incident-review route from section 4; same byte/audit/cache controls. It cannot be used by an uploader merely because they uploaded the object. No preview, OCR, AI or automatic extraction. |
| `POST /private-objects/{id}/clearance` | `{expectedStateRevision, scanObservationId, sha256, decision, reasonCode}`. Human-context RPC resolves reviewer, verifies the exact observation/hash/state and grants, appends the decision/audit, and installs or removes the current clearance pointer atomically. No service-role/AI clearance path. |
| `POST /private-objects/{id}/suspected-phi` | `{expectedStateRevision, reasonCode}` with bounded codes only. The narrowing-only user transition from section 4 invalidates usable clearance and sets normal visibility restriction in the same audited transaction; no content excerpt is accepted. |

Transport progression is `reserved → receiving → stored_unverified → finalized`; `reserved/receiving/stored_unverified → abandoned` is a non-destructive terminal disposition. Errors leave an explicit retry/reconciliation condition, never implicit success. Finalized evidence is immutable even if later quarantine/restriction changes. Store one request fingerprint and one claimed attempt; duplicate or racing puts cannot overwrite. Exact retried finalization returns the established evidence, whereas changed evidence/revision conflicts.

Postgres and object storage do not share a transaction. Handle each partial failure deliberately:

- DB reservation committed, no bytes: retain the reservation; expiry prevents new upload; mark abandoned without deleting history.
- Provider put committed, response or DB receipt lost: keep unreadable. A reconciler inspects only the exact registered key/attempt, reads bytes and verifies evidence before recording `stored_unverified`; it does not assume success or clear quarantine. Do not blindly overwrite on retry.
- Bytes missing, truncated, content/type mismatch, timeout or inconsistent readback: no finalization/clearance. Preserve bounded failure status and quarantine any orphan; no destructive compensation.
- Membership/capability revoked during I/O: finalization's current-state check fails. Already received bytes remain inaccessible and preserved for controlled disposition; revocation never silently deletes them.
- Scan result is duplicated, delayed or refers to another digest/attempt: idempotent exact duplicate or rejected conflict, never a stale result promoted to current.

The upload reservation TTL is a configurable operational limit, not retention/destruction authority. Expiry cannot destroy bytes. Use synthetic known fixtures and a local deterministic scan adapter initially. Mark every such observation `synthetic_fixture`; this demonstrates routing/state behavior only and never proves malware/PHI detection. General scanner/provider selection and limits belong to later activation evidence, not an invented owner approval.

## 7. Quarantine, scanning and human authority

Transport, content safety, visibility and preservation are different dimensions. Do not compress them into legacy `documents.release_state`.

| Condition | Normal bytes / AI | Allowed next action |
| --- | --- | --- |
| No finalized verified bytes | Denied / denied | Retry/reconcile only the exact upload attempt. |
| Finalized; no current result, scan running, error, timeout, unknown type or malware blocked | Denied / denied | Restricted scanner/reconciler processing; safe incident metadata. Malware-blocked bytes do not enter the ordinary human download route. |
| Malware pass; no PHI signal | Still quarantined / denied | Designated, exactly granted human review. `no_signal` is not proof of no PHI. |
| Suspected PHI from scanner, uploader report or human observation | Quarantined; prior normal clearance invalidated / denied | Designated incident procedure and constrained review; no notification with content, no external OCR/AI, no automatic redaction-and-release or deletion. |
| Human `cleared_no_phi` on current hash/scan, no restriction | Exact internal grants only / still denied in this slice | Eligible for explicit internal inspection and future DOC-001 adoption; never auto-release or professional sign-off. |
| Rejected, restricted or ingest closed | Normal inspection denied / denied | Preserve traceability and authorized incident handling; no release fallback. |

A human may resolve a false-positive PHI signal with a recorded `cleared_no_phi` decision and bounded `false_positive_reviewed` reason, after a malware-pass result and the approved handling procedure. The original signal remains immutable. New suspicion or a newly claimed scan attempt immediately invalidates the usable clearance; it cannot resurrect itself after a restriction is lifted. Only a result for the current claimed scan attempt and digest can become current. Quarantine status derives from transport, scan state/result, current decision and a bounded reason (`not_finalized`, `scan_pending`, `scan_failed`, `malware_blocked`, `phi_suspected`, `human_review_required`, `rejected`); it is not a release state. Clearance never automatically removes an independent visibility restriction or preservation hold. An already rejected object needs a new explicit decision, not an update to its history. Any byte change is a new object and needs fresh scanning and human clearance.

No scanner, AI output, uploaded instruction, HTML/PDF content or message can grant permission, change state, launch tooling or approve a file. Untrusted bytes enter a bounded scanner sandbox with no Supabase/service credential, no executing attachments/macros, restricted egress and resource/time limits. A trusted outer dispatcher fetches only the exact object/attempt and persists the typed result; the parser receives bytes and a job identifier, not its dispatcher's privileges. The synthetic adapter proves no real sandbox or detection capability. A provider adapter must disclose what content leaves OS and pass OD-013/014 handling gates before real sensitive content is processed. Scanning itself is not evidence that the platform supports PHI.

## 8. Reads, revocation and signed-URL tradeoff

Membership/profile/object-grant revocation, visibility restriction or ingest closure must deny the next new gateway authorization after the transaction commits, even when the same still-valid Auth token and another legacy role remain. Recheck current database state for each request; no retained application permit or cached ACL survives as authority. Test revocation both before upload finalization and before reading. A client may still possess previously delivered bytes, and a request already authorized/in flight may complete; do not promise recall or instantaneous cancellation of a stream.

Supabase private buckets can serve authenticated requests or signed URLs, but a signed URL is a bearer capability for its lifetime. Current provider docs state that Storage signing uses a dedicated key and URLs are not invalidated by Auth-key rotation; support intervention is the documented revocation route. Membership changes are not an established per-link revocation mechanism. Consequently **disable signed URLs for this increment**; short TTL alone would bound exposure, not prove immediate revocation. Never delete a held file or rotate Auth keys as a purported signed-link revocation mechanism.

If a later download product chooses signed links, record its affected capability and accepted lifetime/exposure tradeoff, test the exact provider behavior, and revise the advertised revocation guarantee. Do not silently weaken C01. A later authenticated direct-Storage read alternative must also prevent signing/list/transform bypasses (operation-aware helpers may help), preserve current version-bound permission and satisfy access-audit coverage. It is not part of this gateway contract.

## 9. Preservation and visibility

`preservation_hold` prevents destruction; `visibility_restricted` denies normal visibility. Neither one grants permission, and hold alone must not hide an otherwise authorized object. Exact incident inspection remains a separate privileged action. Test all four hold/restriction combinations.

Automatic permanent destruction is disabled for **all** objects in this slice, held or not. Rejection, abandonment, expiry, account removal, Auth deletion, cancellation and project closure do not delete bytes or history. Metadata/control changes are audited independently. A later deletion workflow must atomically authorize disposition against current holds, verify exact references/versions, use the Storage API, reconcile metadata/bytes and record actual outcomes under OD-011. This ADR approves no retention duration or deletion authority.

Provider/operator credentials can still delete or overwrite bytes outside application controls; inventory/readback reconciliation must detect missing or mismatched objects and immediately deny serving them. Before real data, test restoration of both database history and the byte inventory, not only a database backup. A preserved manifest is not proof that its blob still exists.

## 10. Audit extension and service provenance

Extend `audit_events_access_event_scope_check` additively for explicit `private_object`, `private_object_grant`, `private_object_scan`, `private_object_clearance` and bounded `private_object_attempt` event families. Keep all accepted access families, legacy rows, append-only guards and ACLs. Do not add an unrestricted `actor_kind='system'` escape hatch or a generic client JSON logging endpoint.

Use this exact proposed event allowlist, with each row's actor and scope separately checked:

| `object_type` / `object_id` | Allowed new event types |
| --- | --- |
| `private_object` / manifest UUID | `private_object_reserved`, `private_object_upload_claimed`, `private_object_upload_received`, `private_object_finalized`, `private_object_failed`, `private_object_abandoned`, `private_object_scan_claimed`, `private_object_phi_suspected`, `private_object_restriction_changed`, `private_object_hold_changed`, `private_object_ingest_closed`, `private_object_read_authorized`, `private_object_read_completed`, `private_object_read_failed` |
| `private_object_grant` / grant UUID | `private_object_grant_created`, `private_object_grant_revoked` |
| `private_object_scan` / observation UUID | `private_object_scan_recorded` |
| `private_object_clearance` / decision UUID | `private_object_clearance_recorded` |
| `private_object_attempt` / server attempt UUID | `private_object_denied` |

Tenant-object events require their real account and subject-record UUID; grant/scan/clearance metadata also identifies the parent manifest. Scan/clearance metadata binds exact object/hash/observation/decision IDs; no raw contents, original filename, extracted text, URL token, credential, raw claims, arbitrary report or free-text request body is logged. Object grants cannot be edited/reparented/restored in place: revoke and provision a new audited grant.

User events use the accepted authenticator/authenticated subject-provenance rule plus current transaction-local action authorization. Technical ingress/scanner/reconciler events retain `actor_kind='system'`, null human actors and `actor_system_key='database_privileged_operation'`. A routine-fixed `operation_source`, server job UUID and runner/build identifier distinguish declared component provenance. These do not prove an independently authenticated worker identity when routines share a service credential. Never label service-role work as a human security reviewer or professional approver; no actor supplied by request JSON is authoritative.

The gateway persists consequential denial outcomes through a separate service-only, tightly typed append routine **after** the failed/denied user transaction. Its actor is the observing system, not an invented active user. Use `object_type='private_object_attempt'`, a database-generated attempt UUID, bounded reason/action and optional verified-subject historical UUID marked as an observation from the trusted gateway. Unknown/unauthenticated subjects remain null. A pre-account attempt may have null account only in this newly checked family. A guessed target UUID is labeled attempted input, not a verified owned object; attach a real tenant only when securely resolved. No client-provided actor/time/correlation is accepted. Validate actual gateway/role provenance and shared-key limitations in independent review before this writer is enabled.

Successful transitions append in the same transaction; audit failure aborts the transition. Read authorization must durably append before bytes are returned; failure denies the read. A completion event means the server finished the send, not that a human opened/read the file. Persisted authorization plus a missing completion is an indeterminate/interrupted attempt, not successful delivery. Gateway denials return safe errors even when audit infrastructure fails, but the missing event must be surfaced as an operational fault; never allow the requested action to compensate.

This collector covers the shipped gateway, **not** every direct Data API/Storage denial, provider operator action or rejected SQL statement. RLS-filtered reads do not trigger it and rolled-back SQL events are not durable. Inventory actual provider logs, access, correlation and retention before M19/SEC-001C parent acceptance; insufficient provider coverage remains an explicit gap, not a passing test. This bounded extension is not the whole investigation/export workflow.

## 11. Future DOC-001 interface: no ingest-access bypass

DOC-001 adds immutable `document_versions` under logical `documents`, with same-account document/object links, server revision ordinal, unique object reference, checksum, media/size and creator/time. Define an internal `adopt_private_object(object_id, expected_digest, target_document_id, expected_state_revision)` transition then—not a placeholder endpoint callable now.

In one database transaction that future transition must verify exact object/document/account/facility context, finalized verified bytes, usable current clearance, no restriction and caller's version-creation authority; insert the immutable version-to-object binding; and set one-way `ingest_closed_at`. The object stays physically immutable. Any now-closed object fails **all** ingest-content paths and ingest grants, including the quarantine route. DOC-001 must supply its own version-bound incident-review route when necessary. Test that stale ingest grants never bypass a version's restricted audience.

All later read/review/signature/release/package grants bind the exact immutable version ID and checksum, not the logical document, an object-prefix, a moving `latest` key or an ingest permission. Any later storage authorization resolves through that exact binding. A release is a separate qualified-human transition with class/state/review/audience checks. New drafts do not supersede an existing release; replacement/withdrawal/supersession are explicit audited transitions. Packages reference canonical versions and recheck each child's current restriction/audience at read time. An old release, uploader grant or prior clearance cannot authorize a different byte revision.

No version relation, backfilled release, adopted marker or usable adoption method is created by this architecture task. In the first implementation, the trusted synthetic close-ingest transition only makes access narrower; reopening is unavailable. Later versions/releases remain a DOC-001 dependency, not a fabricated SEC-001C success.

## 12. Acceptance/test matrix and proof levels
