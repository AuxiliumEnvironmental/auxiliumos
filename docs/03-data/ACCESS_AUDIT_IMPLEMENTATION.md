Implemented locally on 2026-10-08 against input commit `283882ced0f8e7be119f4b3c4c75a3f913572bde`, under the accepted server-provenance section of [ADR-002](ADR-002-RUNTIME-FOUNDATION.md). This is a bounded database increment for M19/C01/C07, not completion of those requirements, SEC-001C, or SEC-001. No storage, release, professional approval, client mutation endpoint, cloud migration, deployed API, or browser acceptance is added or claimed.

## Additive data contract

Migration `20261008154950_access_audit_provenance.sql` was generated with the installed Supabase CLI 2.120.0 using `supabase migration new access_audit_provenance`, then populated. Apply it after the unchanged foundation and identity-directory migrations. The original migration, seed, rows, UUIDs, timestamps, metadata, roles and lifecycle rows are preserved. Existing audit rows receive `actor_kind='legacy_fixture'` and a new database-generated correlation UUID; no authenticated runtime actor is retroactively asserted.

The existing `audit_events` relation gains `actor_kind`, `actor_auth_user_id`, `actor_system_key`, and `correlation_id`. Its actor constraint allows exactly:

| Kind | Required provenance | Meaning |
| --- | --- | --- |
| `legacy_fixture` | Null Auth actor and system key; old profile reference may remain | Historical/synthetic fixture only, never authenticated runtime evidence |
| `user` | Nonnull profile and Auth subject; null system key | Linked active development subject in the trusted gateway context below |
| `system` | Null profile/Auth actor; exact key `database_privileged_operation` | Technical privileged database operation, never a human reviewer, signer or approver |

The legacy default intentionally remains so the unchanged owner-run foundation seed is replayable, including `ON CONFLICT DO NOTHING`. A direct database-owner fixture insert receives the same non-runtime label. All trigger-produced events explicitly set `user` or `system`; neither ordinary clients nor `service_role` can directly insert audit rows.

Only the checked `user_profile` event family may have null `account_id`. Account-access and capability events must retain a real account. Runtime rows require an object UUID and internal-only visibility; unknown event/object combinations fail the mutation. No general pre-account-denial or free-form global-security event contract is invented.

## Recorded changes

`private.audit_access_change()` is an `AFTER` row trigger on `user_profiles`, `account_access`, and `account_capability_grants`. It appends inside the source transaction. A logging failure aborts the source mutation; transaction rollback removes both the change and its event. Row creation, relevant updates and row deletion are covered. `TRUNCATE` is explicitly blocked on these sources because it does not emit row-level delete events.

| Source / object type | Event types | Allowlisted prior/new values |
| --- | --- | --- |
| `user_profiles` / `user_profile` | `profile_created`, `profile_updated`, `profile_deleted` | Profile UUID, Auth link UUID, identity status, immutable link-history flag, demo flag |
| `account_access` / `account_access` | `account_access_created`, `account_access_updated`, `account_access_deleted` | Account/profile UUIDs, membership status, demo flag |
| `account_capability_grants` / `account_capability_grant` | `capability_grant_created`, `capability_grant_updated`, `capability_grant_revoked`, `capability_grant_restored`, `capability_grant_deleted` | Grant/account/profile/facility UUIDs, checked capability/scope keys, revoked-at control value, demo flag |

An account-access object's `object_id` is its profile UUID; combine it with the event's account UUID to identify the composite key. Other objects use their existing primary UUID. A privileged cross-account move emits one event for each affected account, with the same generated correlation, timestamp and safe before/after values. This records an already-permitted privileged transition; it grants no new reparenting or client authority.

Metadata contains only `before`, `after`, `database_session_user`, and `database_request_role`. Display names, bookkeeping timestamps, JWTs/raw claims, credentials, arbitrary request bodies and free text are not copied. A no-op, touch-only update, or display-name-only update emits no lifecycle event. Profile linkage history still comes from the existing immutable guard; attempts to reset history fail with no committed audit entry.

Every event UUID, event timestamp and correlation is generated by the database, ignoring request GUCs and source-row timestamps. Correlation identifies one changed row (and both sides of an account move), not a complete HTTP request or multi-statement transaction. Timestamps may tie and are not a total-order sequence.

## Trust and permission boundary

The trigger is a private, owner-controlled `SECURITY DEFINER` function solely because service provisioning cannot write the audit sink. It pins `search_path=''`, uses qualified names, has no caller parameters or dynamic SQL, and has no `PUBLIC`, `anon`, `authenticated`, or `service_role` execute grant. The trusted migration owner must own the affected application tables and functions; verify ownership on the target before deployment.

`auth.uid()` or decoded claims alone do not prove that SQL originated from a validated bearer token. User classification therefore requires all of:

1. Database `session_user='authenticator'` and the request's actual `SET ROLE` setting is `authenticated`. A function's definer `current_user` is not mistaken for the invoker.
2. `auth.uid()` is a UUID and agrees with the JWT `sub`; protected top-level role is `authenticated` and `is_anonymous` is the JSON boolean false. Missing, mismatched or malformed claims fail closed.
3. The subject resolves to an active, linked demo profile. An after-trigger for that same profile's self-suspension/unlink may use its valid prior state; it cannot use another row's actor payload.

This trusts the configured PostgREST authenticator to validate tokens and set request context. The SQL trigger does not verify signatures. No production user-mutation endpoint is supplied by this increment, so ordinary clients cannot reach this branch through the shipped directory surface. Any future trusted mutation handler needs its own independently reviewed, transaction-local capability checks and concurrency contract; actor provenance is not authorization.

System classification is restricted to direct sessions `postgres`, `supabase_admin`, `supabase_auth_admin`, or `service_role` operating in their own role, or `postgres`/`supabase_admin`/`authenticator` operating as `service_role`. Claims on those sessions are ignored, even if they name a valid user. Unknown session/role combinations fail closed instead of being relabeled as system or human. Auth deletion through `supabase_auth_admin` audits the resulting profile unlink as a technical system operation. Confirm these role names against the actual configured target; custom gateways require review rather than broadening the allowlist silently.

Audit table and column privileges are explicitly revoked from ordinary clients and `service_role`; only server-side `service_role` SELECT is restored for internal diagnostics. Existing client directory SELECT columns/policies remain unchanged. Trigger append does not require runtime EXECUTE grants. Ordinary clients retain no audit read/write access or directory mutation capability. Service-role source provisioning remains available, but direct audit insert/update/delete/truncate and source truncation are denied.

Audit UPDATE, DELETE and TRUNCATE guards also reject casual owner operations. This is not tamper-proof against a database owner/superuser who can change DDL, disable triggers, assume sessions, grant privileges, or restore a database. The same trusted owner can explicitly insert fixtures or other rows; the boundary protects application interfaces, not a hostile database administrator. No new retention period or destruction authority is defined.

## Preservation and fixture-cleanup consequences

The historical `actor_auth_user_id` intentionally has no FK to `auth.users`: Auth deletion does not erase it. Existing account and actor-profile `NO ACTION` FKs are retained, not replaced with cascading deletion or `SET NULL` history rewriting. No new target-profile/object FK is added. Profile-global system events have a null actor profile, so they do not by themselves block removal of an otherwise unreferenced synthetic profile; the historical object UUID remains in the event.

An account that receives access/grant events cannot be hard-deleted while its audit history remains. Likewise, a profile referenced as a user actor or legacy fixture actor cannot be hard-deleted. A failed cleanup deletion rolls back without deleting history. Auth identity deletion remains available and preserves the stable profile and immutable linkage history.

**API harness compatibility:** the pre-audit `tests/api/identity-directory.test.mjs` hard-delete fixture-account cleanup contract is incompatible with this preservation behavior. Its direct audit-probe deletion is also unavailable to `service_role`. Do not run that old cleanup path unchanged against a backend with this migration or suppress its errors. The integration lead must adapt preflight/cleanup before authentic API execution: use an isolated disposable database/transactional fixture lifecycle where feasible, or explicitly retain synthetic account/history records while revoking access and deleting synthetic Auth identities as appropriate. Permanent history destruction requires its own approved retention/activation contract, not a test-only bypass. This bounded patch deliberately does not edit the API harness.

For deployment, verify the current target/migration history and ownership, then apply once in order. The migration is transactional; failed application leaves the prior schema intact. Use a reviewed forward fix for defects. Restoring an isolated test database is not authorization to delete production audit history. No destructive down migration is supplied.
