# Private-object security disposition

Implementation contract for C01/C02/C07 and M13/M19, based on ADR-003 §§3,4,7,9–11 and input commit `6163fc914f68899c6a86d8d6ab12d6c186f7201a`. Additive migration: `20261009065625_private_object_clearance.sql`, generated by the integration lead. Independent review is required before integration/deployment. No cloud application or genuine API acceptance is established by this note.

The finalized transport digest is the immutable anchor. A separate `private_object_security.security_revision` starts at zero and changes on security/grant transitions. Existing reservation/transport RPCs and their **pending-only** scan/clearance fields are unchanged; consumers must use the new security-status RPC for current security state, not reinterpret transport fields.

## Exact RPC boundary

All public wrappers are invoker functions; checked definers are private, empty-search-path, statically qualified and explicitly granted. Every application role—including `service_role`—is denied base-table access. RLS adds defense in depth. Technical operations require the existing `authenticator` → `service_role` context and enabled synthetic reservation config; a direct SQL session with forged JWT settings is not accepted.

| RPC | Caller and contract |
| --- | --- |
| `private_object_security_status(p_object_id)` | Authenticated current uploader with exact facility ingest capability **or** exact applicable object grant, plus current demo profile/membership/account/facility read access. Read-only bounded JSON; no paths, content, filenames, actor lists or counts. |
| `report_private_object_phi(p_object_id,p_expected_revision)` | Same current actor authorization as status. Only narrows access: clears usable clearance, sets suspicion and visibility restriction; returns security status. |
| `decide_private_object_clearance(p_object_id,p_scan_observation_id,p_verified_sha256,p_expected_revision,p_request_id,p_decision,p_reason_code)` | Current authenticated human with separate exact `clear_object` grant. Requires finalized digest/current malware-pass observation and CAS. Never executable by service role. |
| `provision_private_object_grant(p_object_id,p_profile_id,p_capability,p_request_id,p_expected_revision)` | Service-only explicit synthetic recipient provisioning; current recipient profile/membership/facility entitlement required. Capabilities: `inspect_cleared_object`, `inspect_quarantined_object`, `clear_object`. Uploader, legacy roles and account-read grants do not imply any of them. |
| `revoke_private_object_grant(p_object_id,p_grant_id,p_expected_revision)` | Service-only exact grant retirement; remains possible after recipient suspension and ingest closure. No in-place restore/reparent. |
| `claim_private_object_scan(p_object_id,p_expected_revision,p_request_id,p_adapter_kind,p_adapter_version,p_ruleset_version)` | Service-only; **only** `synthetic_fixture` is accepted. Creates immutable server attempt tied to verified digest, immediately invalidating prior observation/clearance pointers. |
| `record_private_object_scan(p_object_id,p_scan_attempt_id,p_verified_sha256,p_malware_outcome,p_phi_signal,p_reason_code)` | Service-only typed synthetic observation; only the current claimed attempt/digest can install its immutable result. No reports, content or extracted text accepted. |
| `set_private_object_controls(p_object_id,p_expected_revision,p_visibility_restricted,p_preservation_hold,p_ingest_closed)` | Service-only synthetic controls; hold and visibility are independent; ingest closure is one-way. No destructive action. |

`p_profile_id` is a grant **recipient**, never an event actor. Database-resolved actors/times/UUIDs are authoritative. Technical provenance records system/null human actors and fixed component/source identifiers; shared service credentials are not separately authenticated scanner identities.

Status keys: `object_id`, `state`, `security_revision`, `verified_sha256`, `scan_state`, `scan_attempt_id`, `scan_observation_id`, `clearance_decision_id`, `malware_outcome`, `phi_signal`, `clearance_decision`, `visibility_restricted`, `preservation_hold`, `ingest_closed`, `security_clearance_eligible`, `quarantined`, `next_action`. A missing or unauthorized ID produces exactly `{"object_id":null,"state":"not_found_or_unavailable"}`. Invalid authentication is distinct (`28000`); mutation denial uses `42501`, stale/current-attempt conflict `40001`, changed idempotent request `23505`, bad typed input `22023`, unavailable lifecycle `55000`. Status is display metadata, never a reusable content/adoption permit.

## State, history and concurrency

Same-account/object/hash composite foreign keys bind finalized transport, security, scan attempts, observations, decisions and current pointers. Evidence is append-only; grants can only gain a server revocation. No cascade deletion or destruction RPC exists. Accepted audit event families remain intact; every consequential new transition audits in its own transaction, and audit failure rolls back the transition.

`pass` + `no_signal` remains quarantined until an explicit current-human `cleared_no_phi` decision. `not_checked` also never auto-clears. Scanner/human/uploader suspicion restricts visibility and invalidates clearance. A `cleared_no_phi` decision resolving suspicion requires `false_positive_reviewed`; the original signal remains immutable. Clearance does not remove a restriction or hold. Hold alone does not suppress security eligibility. Lifting a restriction cannot resurrect a clearance invalidated by suspicion or rescan. `rejected` needs a new decision, not a history update. Malware blocked/error/timeout cannot be cleared by the human RPC.

Claim, observation, grant and decision retries preserve original immutable rows. Claim/grant/decision request IDs are scoped to exact objects (decisions additionally to reviewer); changed retries conflict. Historical decision replay reports `current:false` and cannot reinstall clearance. A superseded attempt's result is rejected. Controls and suspicion use exact current CAS; an unchanged suspicion report at the current revision is a no-op. Grant changes also increment security CAS so an in-flight human disposition must re-evaluate.

User lock order: enabled config, profile, account, membership, facility, directory grants ordered by UUID, exact object grants ordered by UUID, finalized transport, security row. `SHARE`, not `KEY SHARE`, blocks relevant non-key status/revocation changes. Recipient provisioning follows that order; exact revocation locks the grant before security and does not require the revoked recipient to remain active. Technical scan/control operations have no human subject; they lock config, demo account/facility, transport, then security. No provider I/O happens under these locks. Concurrent revocation should either precede authorization or follow its committed transaction; actual two-session target-engine execution remains a separate acceptance gate.

## Deliberate limits and evidence

This increment is synthetic under OD-001/003/011/013. It implements a typed **fixture result boundary**, not an actual scanner, malware/PHI detector, parser sandbox or external provider adapter. Unknown/provider adapters are rejected. No content is interpreted or executed. No content/download/signing/AI/OCR/export/adoption/release route is added; `security_clearance_eligible` is neither professional approval nor document/version authority. A future adoption transaction must recheck all exact context/current state and its own caller authority atomically, then close ingest. The API grant names for inspection confer no content route in this increment.

Focused database checks: `node --test tests/database/private-object-clearance.test.mjs` (39 checks in PostgreSQL/PGlite with simulated Auth). Prepared authentic harness: `tests/api/private-object-clearance.test.mjs`; secure configuration, reviewed deployed migrations, existing synthetic gateway/private bucket and separate execution authorization are required. Its cleanup retains bytes/application/history, retires exact private grants, closes only created ingest objects, then uses the existing audited fixture cleanup. It must never delete object history to make a test pass. No authentic API execution or real two-session PostgreSQL evidence is claimed here. Target advisors, hosted Auth/API, provider inventory/restore, durable denied-attempt collection, incident procedure and qualified-human live binding remain open gates.
