# Private-object reservation boundary

Date: 2026-10-08. Task: `SEC-001C-OBJECT-RESERVATIONS` (issue #86).
Input HEAD: `0773cce60f030084a8a321ec42429d6a91fce838`.
Requirements supported in this bounded layer: C01, C02, C07, M19.

This implements **synthetic metadata reservation and safe status only**. A
reservation is not an upload, a stored file, verified evidence, a scan result, a
clearance or a document version. No bytes are accepted or served. The parent
security, document and audit requirements remain incomplete.

## Implemented contract

`20261008164758_private_object_reservations.sql` was generated by the integration
lead using Supabase CLI 2.120.0 and populated additively after the accepted audit
migration. Old migrations, seed, directory helpers and legacy rows are unchanged.

| Surface | Behavior |
| --- | --- |
| Existing capability table | Adds only `ingest_private_object`, with `scope_kind='facility'` and a required same-account facility. The original three directory combinations remain valid; the directory helper still rejects the new key. |
| `private.private_object_reservations` | Immutable server UUID, private key, creator/profile and historical Auth subject, server timestamps, demo-only state, typed declaration and canonical request identity. Unique `(account_id, created_by_profile_id, idempotency_key)`. Required account/facility/creator-access references use NO ACTION, not destructive cascades. |
| `private.private_object_reservation_config` | One owner-controlled row: disabled initially, maximum declaration size 65,536 bytes, reservation TTL 900 seconds. Bounds are 1–65,536 bytes and 1–3,600 seconds. No GUC, client flag or service-role write can enable it. |
| `public.reserve_private_object` | Authenticated gateway call with `(p_account_id uuid, p_facility_id uuid, p_idempotency_key uuid, p_byte_size integer, p_media_type text)`. Only exact `text/plain`, nonempty declarations up to the configured maximum. No content, filename, actor, time, path, arbitrary JSON or digest parameter. |
| `public.private_object_status` | Authenticated gateway call with `(p_object_id uuid)`. Only the exact original creator with current ingest authority may see status. No list/count/export surface. |

Both RPCs return exactly `object_id uuid`, `state text`, `state_revision bigint`
and `expires_at timestamptz`. The public wrappers are minimal SECURITY INVOKER
delegates to explicitly granted private SECURITY DEFINER routines. Internal
helpers/triggers are not directly executable by application or service roles.
All functions have an empty search path and qualified relation/function names.

The private bucket identifier `os-private-ingest` and generated key
`<account>/<facility>/<reservation>/payload` are private metadata only. They are
never returned by the RPCs. **No bucket is created or configured**, and no Storage
policy, signed URL, content route or successful-upload claim exists.

Declared media type/size are unverified request values. The canonical request is
an immutable server-built JSONB value containing schema version 1, account,
facility, declared size and exact media type; no cryptographic content digest is
claimed. The typed inputs are bounded; request identity contains no filename or
free-form payload. Actual text encoding, byte count and content safety require a
future bounded gateway and verifier.

## Current authority and replay

Every reservation and replay first verifies the `authenticator` session and
actual PostgreSQL `authenticated` SET ROLE state. Protected top-level claims
must be an object with matching nonnull Auth subject, role `authenticated` and
boolean `is_anonymous=false`. User metadata and claimed actor fields confer
nothing. Valid-looking claims on a direct SQL connection, an untrusted session
or the service role cannot manufacture a user reservation.

Current authorization then requires an active linked demo profile, demo
account, active demo membership, same-account demo facility, nonrevoked demo
`view_account`, applicable facility/all-facilities `view_asset`, and an exact
facility `ingest_private_object` grant. Legacy roles grant no access. An ingest
grant never grants content inspection, version creation or release authority.

Profile linkage/status, account/facility demo changes, membership suspension and
grant revocation are checked again on the next request, including replay and
status with unchanged simulated request claims. Auth user deletion may null the
profile link; reservation and historical actor values are retained, and access
then fails. Revocation does not recall previously returned metadata.

Missing and forbidden status return the same four-field row:

```json
{"object_id":null,"state":"not_found_or_unavailable","state_revision":null,"expires_at":null}
```

Invalid gateway/claim provenance raises SQLSTATE `28000`. Failed reservation
authority, including disabled configuration, raises a generic `42501` response.
Invalid declarations raise `22023`; a reused key with different canonical
request identity raises `23505`. UUID/integer type errors occur at PostgreSQL's
typed argument boundary. No error path echoes contents, keys or arbitrary input.

An authorized exact replay returns the original ID, revision and expiry without
inserting another row or audit event. It never extends TTL or recycles the key.
A smaller configuration limit applies to new reservations, not existing exact
replays; disabling reservations denies both new requests and replays/status.
Identical idempotency UUIDs for distinct creators or accounts are independently
scoped. A changed facility with the same creator/account/key conflicts only after
the caller proves current authority for that requested facility.

The persisted state is always `reserved`, revision 1. After expiry, authorized
status/replay derives `expired` from the server clock without changing that row
or revision. This is an operational time predicate, **not a new persisted state
transition and never retention/deletion authority**. No refresh, abandonment,
finalization or cleanup operation is exposed.

## Transactions, locking and preservation

Reserve and authorized status use this consistent lock order:

1. Singleton configuration.
2. Current linked profile.
3. Account.
4. Membership.
5. Same-account facility.
6. Relevant current grants, ordered by UUID.

These are FOR SHARE locks, which block non-key revocation/status updates as well
as deletion. At READ COMMITTED a waiter rechecks changed predicates; higher
isolation levels may require a whole-transaction serialization retry. The
immutable reservation is read after resolving/locking its current scope; status
may first read the private immutable row to discover that scope, without returning
its values before authorization. No provider I/O occurs under locks.

The unique idempotency constraint plus INSERT ON CONFLICT DO NOTHING handles
duplicate inserts; after a conflict the function reads and compares the winner's
immutable identity. Only an actual inserted row fires the AFTER INSERT audit.
Multi-row administrative operations must follow compatible lock ordering and
handle transaction aborts. **Actual concurrent sessions are not proved here**;
the two-session target tests below remain mandatory.

Both private tables have RLS enabled and no application policies. PUBLIC, anon,
authenticated and service_role receive no direct table privileges, even when
provider defaults grant broad privileges. Reservation UPDATE, DELETE and
TRUNCATE are rejected by guards, including privileged ordinary statements and
upstream TRUNCATE CASCADE. Parent reference deletion is blocked by NO ACTION FKs.
No test-only history deletion or immutability bypass is shipped. Database owners
can still deliberately alter/drop schema or disable triggers; this is not WORM
protection against database administrators.

## Protected audit and configuration

The accepted audit constraint is extended only for:

- `private_object` / `private_object_reserved`, with real account and user actor.
- `private_object_reservation_config` / `private_object_reservation_config_created`
  or `private_object_reservation_config_updated`, with null account and fixed
  `database_privileged_operation` system provenance.

Configuration initialization emits one system event; this intentionally adds
history while retaining every original event. Meaningful configuration changes
increment server revision/time and audit safe before/after control values.
No-op updates do not add events. Configuration identity/provenance cannot be
overridden, and deletion/truncation is forbidden. There is no service or client
configuration RPC: only an ordinary trusted `postgres`/`supabase_admin` owner
session may update the narrow configuration columns. Keeping it disabled is the
default; enabling it is synthetic development configuration, not live approval.

Reservation audit has fixed operation source, account/object/actor IDs, safe
facility/state/revision/expiry/declaration metadata and server UUID/time/
correlation. It excludes the object key, bucket, idempotency UUID, raw claims,
filenames and arbitrary request text. Clients and service roles cannot directly
append audit rows. Existing immutable audit guards and ACLs are unchanged.
Audit insertion failure rolls back the reservation/configuration change in the
same transaction. Safe status reads do not fabricate content-read audit events.
Durable failed-attempt collection remains unimplemented.
