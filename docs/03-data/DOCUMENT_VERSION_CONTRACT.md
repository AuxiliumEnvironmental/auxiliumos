# Immutable document adoption (DOC-001A)

Development-only C01/C02/C07/M13/M19 contract, based on ADR-003 §11, the document release workflow/access matrix, and reviewed clearance input `a32a5d008b7a92ce2ccb7f9df8c4ae4547af601b`. Migration `20261009072201_document_versions.sql` was generated by the integration lead. OD-002/003/004/011/013 live bindings remain gated. No hosted application or professional/release approval is implied.

`private.document_versions` binds one finalized ingest object, exact account/facility/document/digest, verified media/size, current scan/clearance evidence, server ordinal/creator/time and an immutable `internal_draft` state. Existing `public.documents` UUIDs and legacy labels are untouched and confer no authority. Ordinal allocation is not a latest-release pointer; a new draft never supersedes another version. No rows are backfilled from labels and no content, review, signature, release, package or destruction route is added.

## Public RPCs

| RPC | Contract |
| --- | --- |
| `list_version_documents(p_account_id,p_after_id=null,p_limit=25)` | Bounded `{items,next_cursor}`. Only exact `view_versions`-granted logical documents with current identity/membership/facility access. Items contain `document_id,account_id,facility_id,title,document_class,document_revision,can_create_version`. No legacy release/version labels or hidden counts. |
| `list_document_versions(p_document_id,p_after_ordinal=0,p_limit=25)` | Authorized `{document_id,state:'available',document_revision,items,next_cursor}`. Items contain `version_id,version_ordinal,object_id,verified_sha256,byte_size,media_type,lifecycle_state,created_at,preservation_hold_at_adoption,preservation_hold,visibility_restricted`. These are authorized metadata only, including current restriction flags—not byte access. |
| `adopt_private_object(p_object_id,p_expected_sha256,p_document_id,p_expected_security_revision,p_expected_document_revision,p_request_id)` | Current authenticated human, current source status entitlement (uploader+ingest or exact object grant), and **both explicit** target `view_versions` + `create_version` grants. Requires exact same scope, finalized digest, current matching malware-pass and human `cleared_no_phi`, no suspicion/restriction/closure, and both CAS revisions. Returns the immutable adoption receipt below. |
| `provision_document_version_grant(p_document_id,p_profile_id,p_capability,p_request_id,p_expected_revision)` | Service-only explicit synthetic recipient provisioning. Capability is `view_versions` or `create_version`; active linked demo recipient/current directory scope required. `p_profile_id` is recipient, never actor. Returns `{grant_id,document_revision,revoked}`. |
| `revoke_document_version_grant(p_document_id,p_grant_id,p_expected_revision)` | Service-only exact retirement, including after recipient suspension. Same response; no restore/edit/reparent in place. |

Adoption receipt keys: `version_id,document_id,object_id,version_ordinal,verified_sha256,byte_size,media_type,lifecycle_state,created_at,preservation_hold_at_adoption,document_revision,security_revision`. Its revisions describe the original adoption, not live permissions. The request UUID is scoped to document+creator; exact retries recheck current source/target authorization and return the original receipt without duplicating version/closure/audit. Changed request fields conflict. New versions/grant changes advance document CAS; only adoption advances the ordinal. The object has a unique version binding.

Lists accept 1–100 items. An unavailable account list is empty; missing/forbidden version detail is exactly `{"document_id":null,"state":"not_found_or_unavailable","items":[],"next_cursor":null}`. Errors: invalid authentication `28000`; unavailable authorization/scope `42501`; invalid typed input `22023`; stale CAS/digest `40001`; changed idempotent request `23505`; uncleared/restricted/closed lifecycle `55000`. No actor/time/path input exists. Every public wrapper is invoker; checked definers and helpers are private with empty search paths, no dynamic SQL and explicit ACLs. All new base tables have RLS and deny all application roles, including service-role direct access.

## Atomic boundary and compatibility

The version BEFORE trigger revalidates authorization and security even for a privileged direct INSERT, and server-assigns all authoritative fields. Its AFTER trigger mandatorily closes ingest and increments document revision/ordinal before writing the adoption audit; either audit failure rolls back all changes. Both adoption and one-way closure have real current-human provenance. Technical grant changes remain system events with null human actors.

The **new** migration narrowly extends the existing security guard/audit allowlist; older migration files remain unchanged. Human closure is permitted only for an exact just-inserted immutable version matching object/account/hash/current scan/current clearance/security revision, current Auth actor, server timestamp and `pg_current_xact_id()` in that transaction. Current source/document authority is rechecked; no caller flag/GUC can activate closure. Every unrelated security field, including preservation hold and clearance pointers, is unchanged. Existing technical closure and all prior guard/audit families remain. Holds are preserved and snapshotted, not interpreted as visibility or deletion authority. After adoption, old ingest grants cannot reopen/scan/report/clear the source; future byte routes must use separately reviewed exact-version authority.

Lock order: config → current profile/account/membership/facility/directory grants → source object grants (adoption) → exact document grants → logical document → document head → finalized transport/security. Grant rows are ordered by UUID. Creation acquires document `UPDATE` directly (no SHARE-to-UPDATE upgrade); reads take SHARE. Scope is anchored by composite FKs without cascades. List-of-documents is a single current-authorization snapshot, not a permit; mutations recheck under locks. Provider I/O is never performed under these locks. Actual concurrent-session target execution remains a required independent gate.

## Verification and next gate

`node --test tests/database/document-versions.test.mjs` passed 38 PostgreSQL/PGlite tests (37 subtests plus parent) with explicitly simulated Auth. The file covers exact bindings, separate grants, stale/hash/request conflicts, pagination/denial, retained-role revocation, malware/error/rejection, hold/restriction separation, immutable history, mandatory server-assigned insertion/closure, rollback and prior technical closure compatibility. It is not genuine Auth/API or target-version/concurrency evidence.

Prepared authentic harness: `tests/api/document-versions.test.mjs`. In addition to the existing secure test configuration, it requires `AUXILIUMOS_TEST_VERSION_DOCUMENT_ID` and optional `AUXILIUMOS_TEST_VERSION_DOCUMENT_REVISION` (default zero). The owner must separately provision a fresh demo logical document titled exactly `Synthetic version API fixture <document UUID>` with a demo facility/account and approved read-only service preflight access. This migration does **not** broaden the legacy document table's ACL or create a logical-document provisioning API. Missing prerequisites fail before Auth creation. The harness never alters the owner-provided document/account/facility during cleanup; it retires only its own generated profiles/access/grants, preserves bytes/versions/audit, and reports retained synthetic Auth IDs for verified operator cleanup. It is prepared, not hosted-executed.

The unchanged shared Auth cleanup helper cannot compose with this borrowed account: its manifest requires every membership pair's account in the owned `client_accounts` IDs, and omitting pairs fails linked-access deletion verification even after retirement. The harness does not misclassify the borrowed account as owned or extend the helper. Owned retirement is exact-read/update/readback verified; all retained IDs and each failure are diagnosed before returning.
