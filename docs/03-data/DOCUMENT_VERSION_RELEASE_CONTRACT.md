# Exact-version synthetic release and bounded content (DOC-001D)

This bounded development slice consumes the immutable version, content, and human review contracts at `acab490`. Migration `20261009184724_document_version_releases.sql` follows `20261009172736_document_version_reviews.sql`. M13/M19 and C01/C02/C05/C07 apply. The integration lead owns the provisional OD-002/003/004 register entries and live activation gates.

A release is an immutable exact-version/digest record approved by a separately assigned human controller. The existing release RPCs provide recipient **metadata only**. The separate, not-yet-deployed released-content extension below supplies a bounded byte-authorization contract. Neither slice sends a notification, signs anything, changes scope or terms, establishes professional qualifications, or affects Moldo. Existing internal `view_content` grants and the internal byte gateway remain independent: a metadata release or withdrawal neither grants nor revokes that internal authority. All owner onboarding grants remain unchanged; no owner reviewer, controller or recipient assignment is provisioned.

## Development policy choices

Only logical documents classified exactly `routine_synthetic_document` are eligible. Existing draft, internal, final-report, executive, legal, agreement, signature and billing labels do not inherit this synthetic class. All identities, scopes, objects, assignments and operations must remain synthetic. Real classification, sensitive-class approvals, professional qualifications, designated people and audiences remain gated by OD-002/003/004/013.

The controller grant is separate from professional review. Routine fixture identities may hold both roles only when each grant is explicitly provisioned; no implied dual role or real qualification is asserted. Release requires an immutable `approved_internal` decision for this exact version/digest. Retirement of its reviewer assignment preserves that historical approval. Retirement of the controller assignment preserves an already completed release but blocks new actions and retries using that retired authority. Recipient access is independently rechecked and does not depend on the continued membership of the historical reviewer/controller.

The human release pins a nonempty set of exact `current_recipient` grant IDs. Newly provisioned recipients are never silently appended. Retiring an approved grant removes its current visibility; a replacement grant ID cannot restore the pinned audience. A separately provisioned, audited `historical_recipient` grant may authorize a new synthetic recipient absent from the original current audience. It works only for a superseded, nonwithdrawn version with current scope and safety; it grants no ordinary-current visibility. This is the explicit synthetic OD-004 historical audience choice, not approval of a live portal policy.

The slice prohibits release of any version whose ordinal is not greater than every previously released version of that document, including after withdrawal. This conservative development constraint prevents rollback and reopening; it is not a permanent product policy. Future re-release/version policies need their own approved contract.

## Public RPC contract

All results are scalar JSON. Public invoker wrappers delegate to private checked definers with empty search paths. No caller supplies actor identity, timestamps, storage paths, URLs, content, notes or arbitrary JSON. The service RPCs require the existing trusted `authenticator` / `service_role` context and do not accept human impersonation.

| RPC | Ordered arguments | Caller and result |
| --- | --- | --- |
| `provision_document_release_grant` | `p_version_id uuid`, `p_expected_sha256 text`, `p_profile_id uuid`, `p_grant_kind text`, `p_request_id uuid`, `p_expected_document_revision bigint`, `p_expected_release_revision bigint`, `p_authority_basis text` | Trusted service; grant receipt. |
| `revoke_document_release_grant` | `p_version_id uuid`, `p_grant_id uuid`, `p_expected_release_revision bigint` | Trusted service; retirement receipt. No restored access/safety/gates needed. |
| `release_document_version` | `p_version_id uuid`, `p_expected_sha256 text`, `p_expected_document_revision bigint`, `p_expected_review_revision bigint`, `p_expected_release_revision bigint`, `p_recipient_grant_ids uuid[]`, `p_request_id uuid`, `p_attestation_code text` | Current explicitly assigned human controller; immutable release receipt. |
| `withdraw_document_release` | `p_release_id uuid`, `p_expected_release_revision bigint`, `p_request_id uuid`, `p_reason_code text` | Current human controller with current internal logical view and active scope; immutable withdrawal receipt. |
| `retire_document_release` | Same as withdrawal | Trusted service narrowing operation; system provenance and no human actor. Works after access, operational gates or safety are disabled. |
| `document_version_release_status` | `p_version_id uuid`, `p_expected_sha256 text` | Current internal logical-version viewer; internal release state and revisions. |
| `document_release_audience_options` | `p_version_id uuid`, `p_expected_sha256 text` | Exact active controller with current internal content and safe scope; explicitly provisioned eligible current recipients only. |
| `current_document_release` | `p_document_id uuid` | Exact approved current recipient; current safe metadata only. |
| `historical_document_release` | `p_version_id uuid`, `p_expected_sha256 text` | Separately granted historical recipient; superseded safe metadata only. |

`p_grant_kind` is exactly `release_controller`, `current_recipient`, or `historical_recipient`; each is an independent exact-version purpose. `p_authority_basis` must explicitly be `synthetic_fixture`. Controller provisioning requires current internal view/content. Recipient provisioning requires current active identity/account/facility directory scope, the synthetic class and current safe exact object, but never creates an internal draft view/content grant. Every grant pins the current profile/Auth identity as well as version/digest.

The release attestation is exactly `released_exact_synthetic_version`. The audience is a one-dimensional array of 1–32 distinct, nonnull grant IDs. Sorting normalizes it as a set for idempotency; the limit is an engineering development bound, not a live audience policy. Every selected grant must currently authorize a scoped synthetic recipient for this exact version/digest. No role label, uploader status, technical clearance, security administration, previous content authorization or AI output supplies controller authority.

Withdrawal reason codes are `release_error`, `audience_change`, or `security_concern`. Human withdrawal rechecks current logical view, active scope and the exact controller assignment. It needs no current content grant, approval or safe object; the existing logical-view helper still requires the reservation operational gate. The trusted service path remains available if that gate or human scope has been disabled. Both current and superseded releases may be withdrawn. Withdrawal never deletes content/history, clears a hold, restores an earlier release, or permits a same-version re-release.

Grant receipts contain `grant_id`, `version_id`, `grant_kind`, observed `release_revision`, `revoked`, and (for provisioning) `authority_basis`. Release receipts contain release/version/document IDs and digest, exact review decision/controller grant IDs, approved recipient grant IDs, prior current release ID, synthetic class, attestation, original document/review revisions, resulting release revision, server time and `metadata_only: true`. A release receipt is historical operation evidence, never a current visibility or download permit.

Withdrawal receipts contain withdrawal/release/version/document IDs, resulting release revision, typed reason, server time and `withdrawn: true`. Internal status contains exact IDs/digest and current document/review/release revisions, nullable release/current-release/approved-review IDs, `release_state` (`unreleased`, `current`, `superseded`, `withdrawn`), `controller_eligible`, `can_prepare_release`, `metadata_only: true`, and `released_download_available: false`. `can_prepare_release` covers controller/approval/version prerequisites only; a release still needs an explicit eligible audience and fresh CAS.

Audience options return exact version/document/digest, observed document/review/release revisions, `metadata_only: true`, and a `recipients` array containing only eligible explicit current-grant IDs, recipient profile IDs and display names. The caller needs a current exact controller assignment and internal content authority; inactive, wrong-scope, retired or Auth-mismatched recipients are omitted. It never enumerates ungranted account members or exposes Auth identifiers. It does not require approval before audience preparation; internal status supplies approval/candidate prerequisites. The selected IDs and revision are observations, and release rechecks every recipient and all CAS inputs.

Recipient metadata contains only release/document/version IDs, digest, ordinal, synthetic class, release time, observed release revision, `visibility: current|historical`, `metadata_only: true`, and `released_download_available: false`. It exposes no storage coordinates, controller identity, audience list or draft versions. Missing, foreign and unavailable records return the same denial. The historical digest is checked only after current entitlement; inaccessible versions do not expose digest conflicts.

## Atomic transitions, retries and narrowing

Private heads, purpose-specific grants, releases and withdrawals have default-deny RLS and explicit ACL revocation. Grants permit only one-way retirement; releases and withdrawals are immutable. Protected BEFORE triggers derive identity, scope, IDs and time and independently recheck authoritative inserts. Mandatory AFTER triggers advance the release head and append protected audit in the same transaction. Failed audit rolls back the authority transition.

Release compares the logical document revision, exact-version review revision, and per-document release revision. Grant provision compares document/release revisions; retirement and withdrawal compare release revision. Existing document and review revisions/ordinals are not advanced by this slice. Locks serialize release-head changes and prevent readers from observing a half-completed replacement/withdrawal. Config, current identity, scope, exact content and object safety locks precede the document/review/release heads and exact release grant locks. No provider I/O occurs within a transaction.

A new draft or review leaves the current release pointer unchanged. Only a completed replacement release changes it, recording the previous current release and a separate supersession audit. Ordinary metadata reads follow the current pointer plus an original pinned active current-recipient grant. Historical reads require the independent historical grant and refuse the current version. Withdrawal records history and clears the current pointer only if it still refers to that release; there is no fallback pointer restoration.

Grant, release and withdrawal idempotency keys bind their full original intent, including expected revisions and audience set where applicable. Exact retries reauthorize current relevant scope, safety, authority and recipients before returning preserved human receipts after unrelated revision advances. A controller replacement cannot revive a retry tied to the original controller grant; a withdrawn release cannot yield a successful release retry. Narrowing retirement/service-withdrawal retries require no restored access or safety. Grant retirement returns its current observed head revision; release/withdrawal receipts preserve the original resulting revision.

Object safety reuses DOC-001C's exact adopted finalized digest/size/type, closed ingest, current malware-pass observation and human `cleared_no_phi` decision, with no suspicion or visibility restriction. Both existing synthetic operational switches apply to new grants/releases and recipient metadata reads. Holds remain independent of visibility and block no metadata by themselves. Legacy logical release labels and immutable adopted versions remain unchanged.

Errors are `28000` for invalid Auth/service provenance, `42501` for unavailable/unauthorized operations, `22023` for invalid typed inputs, `40001` for stale revisions/digests, `23505` for changed idempotent intent, and `55000` for illegal history/re-release transitions. Table ACLs also deny direct access with `42501`.

## Released-content extension — implementation pending executable verification

This extension is based on GitHub input `db0f003d616855bad19dca5fc18d38eefac1d6f1`. The CLI-created additive migration `20261009194030_document_release_content.sql` follows the metadata release migration. The existing metadata RPCs, their flags, existing grants and the internal content gateway remain unchanged. No owner, controller, professional reviewer or recipient is provisioned. There is no cloud deployment or live activation in this extension.

| New RPC | Ordered arguments | Authority and result |
| --- | --- | --- |
| `authorize_document_release_content` | `p_release_id uuid`, `p_expected_sha256 text`, `p_visibility text`, `p_request_id uuid` | Current authenticated recipient only; an immutable authorization binding. |
| `record_document_release_content_result` | `p_authorization_id uuid`, `p_outcome text` | Trusted service only; bounded system observation of an existing authorization. |
| `record_document_release_content_denial` | `p_request_id uuid`, `p_attempted_release_id uuid`, `p_observed_auth_user_id uuid`, `p_reason_code text` | Trusted service only; bounded denied-attempt observation. Attempted release and observed subject may be null. |

The scalar authorization result has exactly `authorization_id, release_id, version_id, recipient_grant_id, visibility, object_id, verified_sha256, byte_size, media_type, bucket_id, object_key`. It is an authorized database-to-gateway manifest, not a reusable bearer permit. Storage coordinates never appear in gateway responses or error/audit metadata. Public authorization RPC callers still need their current exact recipient entitlement on every invocation; knowing an object path supplies no direct Storage permission.

Visibility is explicitly `current` or `historical`. Current requires the exact release to remain the document's current pointer plus the originally pinned, active current-recipient grant. Historical requires a superseded, nonwithdrawn exact release and a separately provisioned active historical grant. There is no fallback or automatic audience expansion when a release is replaced, withdrawn or a grant changes. Both modes retain current synthetic identity/account/facility directory access, both operational gates, exact finalized object/digest/size/type, closed ingest, matching scan/clearance, no PHI suspicion and no visibility restriction. A preservation hold alone remains independent of visibility.

Authorization idempotency is scoped to the verified Auth subject and request UUID. The full intent is exact release, digest and visibility. Every retry rechecks all current authority/safety and additionally requires the original recipient grant and profile. A retired historical grant replaced by a new grant may authorize a fresh request but cannot revive an earlier authorization. Changes of intent conflict (`23505`); missing, foreign, wrong-digest or currently unavailable releases deny with `42501: not_found_or_unavailable`. Invalid typed input is `22023`; invalid authenticated/service provenance is `28000`. The existing metadata digest-conflict behavior is preserved separately.

Three private tables hold authorizations, results and denials, with default-deny RLS and no direct application privileges, including service role. Protected BEFORE triggers derive exact scope, object, recipient, identity, IDs and timestamps, and independently check current authority. Protected AFTER triggers append audit atomically. All authorization/history/result rows are immutable. Audit failure rolls back the associated write. Public functions are invoker wrappers around private checked definers with empty search paths; private helpers and trigger functions are not application-callable.

Outcome is exactly `response_prepared`, `provider_failure`, `integrity_failure`, or `access_changed`. Results are idempotent per authorization/outcome and remain recordable after narrowing. They accept no actor, time, file path, URL, free text, arbitrary metadata or delivery claim. Denial reasons are exactly `unauthenticated`, `forbidden_origin`, `method_not_allowed`, `invalid_request`, `not_found_or_unavailable`, or `backend_unavailable`. Denial audit has a null account and human actor; an observed subject is explicitly not human authority or an existence oracle. The shared trusted service context is not independent worker attestation: it can report bounded system observations, not prove bytes were delivered or read.

The separate route is `GET /document-release-content/{releaseId}/content?sha256={digest}&visibility={current|historical}`. Canonical parameters are strict; ranges, cache validators, request bodies, duplicate/unknown parameters, arbitrary storage coordinates and transformation options are rejected. The gateway verifies the current user through Auth and invokes the authorization RPC in that user's context before provider I/O. A separate server client reads only the returned private object. Provider fetches reject redirects and foreign origins, enforce time/body bounds before SDK buffering, and check 64 KiB maximum, exact size, MIME, UTF-8, synthetic marker and SHA-256.

After buffering/verifying bytes, the gateway invokes authorization again using the same request UUID, digest, exact release and visibility. Every field of both immutable bindings, including recipient grant, version, object and authorization ID, must match. It records a valid `response_prepared` receipt before returning an attachment with private/no-store, no-sniff and sandbox headers. Any authorization, integrity or required result-audit failure returns no file bytes. No signed URL, authorization cache, provider headers, token, path, raw provider error or service key is exposed. The endpoint has its own synthetic-only environment namespace and defaults to **disabled** until explicitly configured by the integration lead.

These are separate short database transactions; no lock spans provider I/O. Replacement, withdrawal, grant retirement or scope/safety revocation before the second check denies the response. A narrowing change after the last committed authorization can race the audit and outgoing response. `response_prepared` proves only the trusted gateway prepared bytes; it is not delivery, opening, inspection, approval or byte recall. No atomic delivery or in-flight cancellation guarantee is claimed.

Focused evidence entry points are `tests/database/document-release-content.test.mjs`, `tests/unit/document-release-content-gateway.test.mjs`, and `tests/unit/document-release-content-entrypoint.test.mjs`. Database checks use PostgreSQL/PGlite with simulated Auth; gateway/entrypoint checks inject provider boundaries. At this checkpoint the executable workspace is unavailable: these tests and source require completion/execution, independent security review and a reviewed integration CI gate. No PostgreSQL execution, hosted Auth/API/browser journey, actual Storage read, concurrent-session race, cloud deployment or full release acceptance is claimed.
