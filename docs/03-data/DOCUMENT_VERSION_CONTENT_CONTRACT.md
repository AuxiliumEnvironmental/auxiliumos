# Exact-version internal content authority (DOC-001B)

Development-only C01/C02/C07/M13/M19 implementation on input `9850848f52233e09b58b9b16e9fc517e475b520a`, consuming immutable adoption migration `20261009072201_document_versions.sql`. The integration lead CLI-created additive migration `20261009080505_document_version_content.sql`. Earlier migrations, seed, legacy document labels and security guards are unchanged. This is internal synthetic content authority, not professional approval, release/audience authority, signing, packages, deletion, a scanner or proof of delivery.

## Frozen public RPC contract

Every result is a **scalar JSON object**, not a set/list. UUID fields below use PostgreSQL `uuid`; digests, outcome and reason use `text`; revisions use `bigint`.

| RPC and ordered parameters | Caller and result |
| --- | --- |
| `authorize_document_version_content(p_version_id,p_expected_sha256,p_request_id)` | Current user context only. Exactly `{authorization_id,version_id,object_id,verified_sha256,byte_size,media_type,bucket_id,object_key}`. Records durable authorization before returning the immutable manifest binding. |
| `provision_document_content_grant(p_version_id,p_expected_sha256,p_profile_id,p_request_id,p_expected_revision)` | Service only; `p_profile_id` is the recipient, never a human actor. Fixed capability `view_content`. Returns `{grant_id,content_revision,revoked}`. |
| `revoke_document_content_grant(p_version_id,p_grant_id,p_expected_revision)` | Service only. Same grant receipt; retirement remains possible after recipient membership, directory access or either enable switch is removed. |
| `record_document_content_result(p_authorization_id,p_outcome)` | Service only. Returns `{result_id,authorization_id,outcome}`; accepts only `response_prepared`, `provider_failure`, `integrity_failure`, `access_changed`. |
| `record_document_content_denial(p_request_id,p_attempted_version_id,p_observed_auth_user_id,p_reason_code)` | Service only; attempted version and observed Auth subject may be null. Returns `{denial_id,request_id,reason_code}`. Reasons: `unauthenticated`, `forbidden_origin`, `method_not_allowed`, `invalid_request`, `not_found_or_unavailable`, `backend_unavailable`. |

Authorization request UUIDs are scoped to the **verified Auth subject**, with version and digest as the immutable request tuple. Exact retries first recheck **current** authority and safety and then return the same original authorization ID and binding. Changing version or digest under the same subject/request conflicts (`23505`). The same request UUID under another verified subject is an independent operation. Historical authorization is **not a bearer permit**. Revocation denies both a fresh UUID and retry of an earlier successful request; the old audit record remains immutable.

Grant requests are scoped to exact version plus request UUID; recipient, digest and expected content revision form their immutable tuple. Each version starts at revision zero. A new grant or retirement increments only its content revision, not the logical document revision. Exact provision retries recheck current synthetic recipient scope and return the existing grant with current revision/revoked status. Changed tuple conflicts (`23505`); stale CAS or grant digest mismatch conflicts (`40001`). A grant cannot be edited, reparented or restored. Re-granting requires a new history row/request. Exact retirement retries use their original expected revision and do not increment again. Replacement drafts do not inherit content grants, including when their hashes happen to match.

Results are immutable and idempotent per authorization/outcome pair. Distinct allowed outcomes can each record a system observation for retried processing. `response_prepared` means only that the trusted gateway prepared a response—not sent, delivered, opened, inspected or approved. Denials append a new server ID per call. Both observation routines remain callable after authorization or enable switches are revoked; neither grants byte access.

Authorization absence, wrong version/digest, missing grants, scope removal and unusable safety state all raise `42501` with the exact message `not_found_or_unavailable`. Invalid Auth provenance raises `28000`; malformed typed input raises `22023`; changed request tuple raises `23505`. Grant stale CAS/hash is `40001`; illegal history transitions are `55000`. ACL failures may independently be `42501`. There are no actor, time, bucket, key, URL, error-text, arbitrary JSON or delivery-claim input parameters.

## Current authority and byte boundary

A read requires all of the following in the current short database transaction:

- Authenticator/authenticated provenance, nonanonymous verified subject, active linked synthetic profile, active account membership, synthetic account/facility, and current directory `view_account` plus exact facility or `all_facilities` `view_asset` grants.
- An exact logical-document `view_versions` grant **and**, independently, an exact version/digest/recipient `view_content` grant. Uploader equality, ingest/clearance grants, administrator/other legacy roles, metadata visibility and prior authorizations add no content authority.
- The immutable synthetic `internal_draft` version; its exact finalized transport digest/size/type; closed ingest; the current matching adoption scan and human clearance; malware `pass`, `cleared_no_phi`, matching current scan attempt/observation/digest, and no suspicion or visibility restriction.
- Both synthetic operational switches enabled. A preservation hold is deliberately not a visibility predicate.

`private.document_content_config` is inserted with `enabled=false`, `synthetic_only=true`. Only an ordinary privileged owner session (`postgres`/`supabase_admin`, not a switched application role) can change its enable field; identity/revision/time are server-assigned and every actual change is audited. This operational switch is separate from OD-001/003/013 live-authority activation gates; it approves no real files, recipients or scanner. Existing private-object configuration must also be enabled. No service table ACL or new configuration RPC is added.

Nonmutating authentic-harness preflight is supported through the service grant RPC: `p_version_id=null` with otherwise valid typed parameters yields `22023` **only after** both enable checks pass, and before any head/grant write. Disabled content or ingest configuration yields `42501`; a missing RPC remains an application/deployment prerequisite failure. This ordering is part of the pinned migration contract, covered by a zero-write test. It is not a general configuration-discovery interface.

The gateway must use the verified caller's user-context authorization RPC immediately before provider fetch and again immediately before serving, with the **same** request UUID. Both returned bindings, including authorization ID, must match. The gateway separately verifies fetched SHA-256/length/type against the immutable binding, records its bounded result, and fails closed if authorization, integrity or required audit fails. It must not cache this authorization, issue signed links, expose arbitrary keys, transform content, or claim SQL proves byte delivery. The database performs no provider I/O. Already delivered bytes cannot be recalled; revocation after the last committed check cannot retroactively cancel them or guarantee in-flight cancellation.

## History, provenance and locks

The six new private tables are configuration, per-version heads, grants, authorizations, results and denials. Every base table has RLS and denies all direct application-role privileges, **including service role**. Public functions are invoker wrappers; checked definers/helpers are private, have empty search paths and explicit execution ACLs. Mandatory BEFORE triggers validate authority/CAS and server-assign scope/provenance even for a privileged direct insert. AFTER triggers advance grant CAS and append audit in the same transaction. Audit failure rolls back the associated grant/head, authorization, result, denial or configuration transition.

Read lock order is content config → existing ingest config → profile/account/membership/facility/directory grants → exact logical grants/document → exact content grant → finalized transport/security. Grants follow configuration/directory/document then per-version head; retirement needs only head then exact grant and does not depend on now-removed recipient authority. Reads never acquire a content head. Public mutation paths acquire the head directly before grant changes; no SHARE-to-UPDATE read upgrade or lock spanning provider I/O is introduced. These are reviewed design properties, **not executed concurrent-session proof**.

| New audit family / event | Actor and safe metadata |
| --- | --- |
| `document_content_authorization` / `document_content_authorized` | Real current user; object ID is authorization ID. Metadata: `version_id,document_id,object_id,verified_sha256,content_grant_id,request_id,meaning:'authorization_only'`. |
| `document_content_grant` / `document_content_grant_created` or `document_content_grant_revoked` | System; object ID is grant ID. Metadata binds exact version/document/hash, recipient profile, `view_content` and content revision. |
| `document_content_result` / `document_content_result_recorded` | System; object ID is result ID. Metadata: `authorization_id,version_id,object_id,verified_sha256,outcome,meaning:'system_observation_not_delivery'`. |
| `document_content_attempt` / `document_content_denied` | System; object ID is generated denial ID. Metadata: `request_id,attempted_version_id,observed_auth_user_id,reason_code,meaning:'system_observation_not_human_authority'`. |
| `document_content_config` / `document_content_config_created` or `document_content_config_updated` | System, null account; enabled/synthetic/revision only. |

Each adds fixed component `document-content-v1`, table-named operation source and database session/request role. System events have null human actors and `database_privileged_operation`. A verified subject supplied by the trusted gateway is merely an observation, not an authenticated human action. Denial account is resolved only if that subject currently has active synthetic directory and exact logical metadata visibility for the attempted version; otherwise null. Raw bytes, filenames, paths/keys, claims, tokens, errors and free text are absent from audit metadata. Shared service provenance does not authenticate an independent worker identity. Direct provider/API denials outside this gateway are not covered by these collectors.

## Preserved failing regression and narrow C02 correction

Before the compatibility correction, the focused command `node --test tests/database/document-version-content.test.mjs` reproduced a real failure in `hold=true and restriction=false remain separate`: after exact adoption and grant, `set_private_object_controls(object,adoptionSecurityRevision,false,true,true)` removed `current_clearance_id`, so authorization failed with `42501: not_found_or_unavailable` in `private.lock_document_content_access`. The first four-state fixture also initially used the wrong control argument order/closure flag; those fixture mistakes were corrected separately. The subsequent 37-test run retained this genuine hold-only failure (and an unrelated seed transaction fixture failure) before code correction; it was not relabeled a pass.

The old routine cleared clearance whenever `p_ingest_closed=true` and **any** control changed, even though adoption had already closed ingest while preserving valid clearance. The new migration replaces **only** `private.set_private_object_controls`, changing clearance invalidation to `p_ingest_closed and s.ingest_closed_at is null`. First technical closure still invalidates clearance; already-null clearance stays null; existing one-way closure, CAS, checked service provenance, security guard and audit behavior remain. Adding/removing a hold or restriction on an already adopted version does not itself erase its immutable human decision. Restriction still denies, and removing it cannot manufacture absent clearance. No old migration is edited. Independent review must specifically re-review this compatibility replacement before deployment.
