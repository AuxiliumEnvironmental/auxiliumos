# Master control and chat protocol

Effective October 11 owner correction: F02-F05 development is concurrent on isolated branches. Integration is ordered. PARALLEL_DEVELOPMENT.md and ACTIVE_TASKS.json supersede the original serial-development restriction. All other source, evidence and delivery protections remain.


## Authority and ownership

Latest explicit owner instructions govern requirements. Current reconciled source establishes implementation facts. This program adds the requested feature scope without replacing the OS destination or the preserved capture/editor work. No promise of zero defects, universal compatibility or complete foresight is supportable. Convert each requirement and discovered risk into a bounded implementation decision and evidence row.

The Astra master is the sole integrator and owner of shared model contracts, version admission, migrations, package/lock changes, renderer coordination, source transfer, release receipts and canonical queue. `source:BUILD_QUEUE.json` remains the implementation queue. Program task IDs refine it; GitHub issues and this package are references, not competing schedulers. `ACTIVE_TASKS.json` records exact per-branch leases only; it is not a second work queue.

The owner authorized agents. Use them when a bounded subtask or independent review saves work. There are four owner-authorized feature chats. Within each, use one implementer and a bounded reviewer only where it saves work. No reviewer quota or duplicated full-suite checking. Use separate worktrees or exclusive files. Never let two agents or Lovable and a local worker edit the same files concurrently. A reviewer must inspect the real diff; a worker summary is not independent review. Do not create an agent for a trivial color edit merely to satisfy a quota.

## Activation, execution and communication

1. Master reads current source ref, working tree, open operations and task dependencies once. Check the existing Lovable agent status before any remote request. Dirty/newer work is preserved and reconciled; never reset from this archive.
2. Record a separate activation per isolated feature branch with task ID, base commit, source root, known host refs, contract revision, exact writable paths, development and integration dependencies, acceptance rows and named owner. Proposed path families in feature packets are not an unlimited write grant; resolve the final paths here.
3. The feature chat reads the short common files plus its packet and relevant source only. It states the first incomplete action, resolves routine engineering details with recorded decisions, and implements one coherent feature. It must not start the next feature after finishing.
4. A contract request states the precise incompatibility, smallest proposed change and affected consumers. Master updates the shared decision, then the worker proceeds. Do not require the human to repeat authorization for an ordinary helper, valid migration adapter or reversible fix already in scope.
5. If a concrete product ambiguity matters, do useful independent work first. Put it in the decision ledger with a recommendation and consequence. Do not silently label a proposed meaning as the owner's decision. The open cutout meaning is such a boundary; colors and private helper names are routine design choices.
6. Worker returns the structured handoff, actual diff/commit, concise test evidence and remaining platform gaps. Master reviews conflicts and changed risks, integrates in dependency order, accepts the composed result or returns specific defects, then updates the ledger. Other isolated feature work can continue. Separate chats hand off through these files/links or text carried by the owner; no assumed cross-chat mailbox.

## Efficiency rules

- Read old evidence only when a claimed result matters to the changed paths. Use `rg` and targeted reads rather than recrawling archives.
- Before a check, name the defect or requirement it can establish. Reuse valid evidence with matching relevant inputs, dependency/configuration versions and environment scope.
- Use one fixture with asymmetric rooms, angled/bent hosts, a raised window, different ceiling heights and a hole. Extend it as features arrive. A parameterized table covers kinds/sides; do not duplicate the same full journey for every color or object label.
- Build/typecheck changed deliverables once per accepted candidate. A necessary fix invalidates only relevant results. No broad OS, native, database, offline or export rerun when the changed code cannot affect it and no required release gate demands it.
- Documentation-only work requires reference/coverage/readback verification, not product suites. Test count is not a progress metric. Stop optional testing once the concrete risks are addressed.
- Lovable receives a bounded implementation or exact transfer request, not repeated broad prompts to re-test unchanged work. Preserve its route, offline shell, strictness, auth scaffolding and unrelated source.

## Completion vocabulary

Use `planned`, `in_progress`, `branch_implementation_complete_pending_integration`, `code_accepted_with_platform_gaps`, or `delivered` with explicit evidence. A branch-local result is not integrated acceptance. Platform fields remain independent: source committed; core verified; UI exercised; host source matched; host built; web served; OS generated/integrated; Apple assets prepared; Apple compiled; simulator exercised; device verified. Never collapse these into a single checked box.

A blocked physical-device gate does not force endless checking or stop unrelated source features. Master may continue the sequence after code/contract acceptance while retaining the gate. Overall completion still requires all requested platform rows, or a clearly recorded owner-approved scope change. No unsupported percentage or background-progress claim.

## Protection and long-term maintenance

Keep standalone drafts usable without OS connectivity. Keep namespaces, expected revisions, immutable releases, source provenance and disabled publisher behavior. URL context never grants authority. Do not change Moldo/companion permissions or OS business data as a side effect. Keep capture originals intact.

Change maintained source once; derive host/Apple/OS outputs through documented packaging. Do not hand-edit generated bundles or preserve three diverging editors. Every new persisted feature includes its migration/admission/export path and a capability/version decision. Retain backward fixtures, reject unsupported new versions without modifying the original, and provide a documented extension boundary without speculative framework work.
