# AuxiliumOS UI audit

Audit source: `148d74d9720f0799e5d845bb789cd3fc3f43feb8`. The integration lead separately retrieved Lovable revision `8d59d22271287d7e1185fc3a65b1cfd548c4e82a` and reported matching shell, Home, forms, context and styles. Document controls differ; generated Spatial source has its own manifest. No live product, repository or database change was performed by this audit.

## Finding

The owner is right that the last UI push did not produce a coherent operating product. The core problem is not merely visual styling. A development catalog of modules, fictional illustrations and private planning forms occupies the places where role-specific work queues, actual records, governed actions and integrated tools should be. Useful safety and persistence controls exist, but users must absorb development implementation details, repeatedly select context, and navigate disconnected surfaces. The current UI therefore communicates the breadth of the plan much better than it demonstrates the value of operating it.

This does not mean the implementation should be discarded. Preserve the directory, intake, versioning, denial checks, exact-operation retry and conflict protections. Repair the shared interaction model and build complete, evidence-backed journeys on that foundation. Do not perform another bulk cosmetic generation pass or relax permissions to make a demo appear finished.

## Fresh browser observations

The focused local fixture session completed in 15.8 seconds after correcting one audit-harness cleanup expectation. Four behaviors were reproduced: loading an example replaced dirty content without confirmation; selecting the account/facility needed to save erased the open draft; a synthetic background/foreground visibility event erased unsaved work; and navigating away through the in-app menu and returning erased unsaved work. The resulting title and inclusion fields were empty in the latter three scenarios. These are actual observed local UI results, not merely inferred risks.

At 390 × 844, the Scope context selector begins at y=1,289 and “Prepare draft” at y=1,679. The page has no horizontal overflow. Thus the prior no-overflow gate can pass while the task remains almost two screens below the top. Spatial at 1440 pixels rendered the breadcrumb “Workspace” and document title “AuxiliumOS”.

The fixture deliberately blocks unhandled network calls. Documents list was unhandled by the borrowed directory fixture, so screenshot 05 shows the service-unavailable fallback caused by that interception. It is not evidence that the real document service is down. No browser page exceptions were recorded; the Vite log contains missing generated source-map warnings. No drawing interaction, project handoff, real document transaction or mobile software keyboard was tested in this session.

## Keep what is already sound

The shell has a skip link and mobile dialog; module tabs support arrow/Home/End keys. Source checks clear stale scoped data and reject late reads. The draft save path distinguishes confirmed save, readback failure, uncertainty and conflict and retries exact frozen operations. Document review/release controls separate historical receipts from continuing authority. Demonstrations carry sample labels and avoid pretending unknown financial values are zero. Spatial CSS is scoped under `.spatial-workspace`; no global-reset collision was found in the reviewed generated CSS.

These should be retained and strengthened, not removed as “too many safeguards”. The correction is to make the common task simple while the application continues to enforce these boundaries underneath.

## Recommended repair sequence

1. **Protect work and context.** Resolve UI-03/04/05/06 first. Reuse safe scope invalidation, exact retry and revision behavior. Confirm an interrupted save cannot be duplicated or confused with a discarded draft.
2. **Build one complete role-specific operating journey.** Use the existing intake/account/document foundation and canonical states. Replace the generic Home with current assigned work and exact links. Carry the same context into scope/authorization/project/review. Deliver the client projection alongside internal work so a demo shows value to both.
3. **Normalize shared presentation.** Establish one context header, status vocabulary, action hierarchy, list/detail/editor/review patterns and route labels. Apply them per owning workflow with actual data contracts. Do not manufacture a new workflow merely to fill a tab.
4. **Integrate tools in their proper role.** Maintain independent source ownership; prove launch, persistence, exact-version handoff and project/audience boundaries. Keep Moldo independent and the latest separately authorized Spatial goal explicit.
5. **Finish the remaining original modules and launch checks.** Use the route/action matrix and M01–M20 acceptance to track real capabilities. Validate representative large accounts, actual mobile interactions, each permitted audience and release/recovery behavior. No false completion percentage from screen count.

## Assumptions, risks and decisions

Assumption: the full existing twenty-module destination and canonical spine remain controlling; the owner requested reconciliation, not a reduced product or speculative redesign. Risk: copying the current preparation catalog into a polished theme would preserve the functional disconnection. Risk: an archive or Lovable-only replacement could discard newer document controls or Spatial work; reconcile exact source versions first.

No new core object, permission role, document state or professional authority is proposed here. Presentation grouping and route aliases are engineering details to record in the UI contract. Live authority bindings and the owner's questioned AI scope require the main package's decision reconciliation. The independent tool deployment/host decision must match existing approval rather than silently treating a route as an independent product.
