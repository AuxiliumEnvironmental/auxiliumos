## Proposed portal defaults

The historical Master Map proposes these starting experiences. Visibility remains subject to enabled modules, record assignment, document class/release state and action permissions enforced at the backend.

| Context | Suggested first views | Other available views when permitted |
|---|---|---|
| Simple project client, individual owner or restoration client | Projects, request, status, released documents and messages | Agreements/invoices, account |
| Public adjuster or attorney project client | Projects, new request, project documents/reports and questions | Agreements/invoices, account users and restricted dispute materials by explicit grant |
| Property manager | Properties, unit/site requests, open approvals and project history | Released documents, messages, agreements/invoices, authorized portfolio rollups |
| Enterprise, healthcare, industrial or multi-site account | Facilities, active incidents, requests, site passports and readiness | Executive dashboards, vendors, QBRs and financial ledger only for assigned capabilities |
| Site Champion within an enterprise account | Assigned facility, report incident, site information and next actions | Permitted site tasks and released site/project documents |
| Billing-only user | Invoices, payment/PO records and billing questions | Minimal project references necessary for billing, without automatic technical-report access |
| Vendor user | Assigned work, instructions, upload/closeout and credentials | Explicitly granted documents; no unrelated client, financial or executive access |

Client type, portal mode and role are separate. A Site Champion is not a separate customer type. A vendor is an external participant rather than automatically a client account. Program/MSA and Portfolio remain optional layers for ordinary work.

## Account and configuration fields

Recover the workbook's legal account name, DBA/brand, proposed tier, client tags, internal primary/secondary owner, billing contact, signer, project/change/sampling/emergency approvers, payment terms, PO requirements, rate schedule, MSA status, templates, enabled/hidden modules, custom terminology, safety/access defaults, retention, external sharing and export rights. Proposed account tiers are configurable presets; the historical workbook did not contain approved tier names, prices or entitlements.

Each client-type configuration needs a stable ID/version; plain-language terminology; first/conditional request tiles; common misunderstandings; required questions; suggested add-ons; default deliverable proposals; safety/scope reviewer triggers; source and rationale; effective dates; and activation status. Permission expectations are references to the actual role/access model, never automatic grants.

## Onboarding and interaction defaults

Use invite-based access as a proposed development default, with explicit account/site/project assignment and separate signer/approver/billing capabilities. Final identity configuration remains OD-012. Onboarding should identify the user's permitted tasks and explain where status, next actions and support live. Site Champions and frequent requesters should have concise role-specific quick references, as proposed in the alternate June 14 workbook.

The original command-center design requires account, linked object, status, priority, owner, next action, due date, blocker, reviewer requirement, client-facing status and last activity on actionable queue items. Screens should make those relationships clear without exposing internal technical labels to clients. Use saved templates, asset prefill, repeat prior request and help-classify paths with current-rule revalidation.

## Moldo boundary

Current user direction adds an independent Moldo operating application. Moldo-only staff/managers continue in Moldo and receive no OS access by implication. Authorized Auxilium leaders can view permitted Moldo projections in OS; enterprise clients see permitted portfolio-related records and released outputs. Ordinary Moldo clients retain their Moldo experience. The integration must honor OD-016 and the agreed record-ownership architecture. The companion app remains deferred.

## Dependencies and acceptance

- Synthetic users from different accounts, sites and capabilities see only appropriate records and actions; hiding navigation is insufficient evidence.
- Account type changes affect presentation/configuration without rewriting existing authority, signed terms or record ownership.
- A requester cannot sign or approve merely because they submitted the request. A billing user cannot gain report access through invoice links.
- The same underlying record can be presented simply to clients and with technical detail internally, without duplicating operational truth.
- Implement phone, tablet and desktop completion of the primary actions with clear status, next action and error recovery; do not count a static responsive mockup as workflow acceptance.
- Keep no-PHI instructions and appropriate reporting boundaries in sensitive contexts. Notifications and external sharing follow OD-017 and recipient permissions.
