# Execution protocol
Effective 2026-10-08. This is the current implementation workflow for the full destination. Use docs/08-ai/FULL_STACK_BUILD_PROTOCOL.md for the existing Lovable/Supabase path, feature contracts and backend-through-UI acceptance. Cursor is optional.

## Sources and completion
BUILD_STATE.json records observed facts and access gaps; BUILD_QUEUE.json records work/dependencies; REQUIREMENTS.json records complete acceptance; OWNER_DECISIONS.json records provisional business choices. Do not mirror those registers into independent competing status documents. Historical plans supply intent, not proof of implementation. Preserve original plans and the source/version used when a requirement changes.

`planned`, `ready`, `in_progress`, `implemented`, `blocked` and `deferred` are declared work states. Verification is computed from current passing evidence, not a hand-edited `done` flag. A task with code but no current evidence remains unverified. Runtime requirements additionally demand appropriate database/API/browser evidence before full release. UI stubs, TODOs, fake success messages and static checks cannot complete a product module.

## Task lifecycle and specialists
1. Resolve current Git source and any incompatible newer work. Select a dependency-ready task; expand large roadmap tasks into reviewable implementation slices with acceptance IDs, expected files, risk, branch and next action.
2. Pin input commit/tree, relevant source documents, interface contract, test scope and decision defaults. A worker packet contains the task plus those inputs, not every prior conversation.
3. Use one lead/integrator. Spawn a specialist only when it reduces an independent bottleneck. Prefer at most three concurrent specialists; fewer for shared schema/auth work. Use fresh worker context after a bounded deliverable. On tools without isolated worktrees, enforce disjoint file allocation. Shared lockfiles, migrations and root registers have one writer.
4. Build, inspect actual changes and run meaningful affected checks. Include untracked files in allocation review. Run `node scripts/os-control.mjs allocation TASK changed-paths.txt` with paths captured from both the Git diff and untracked inventory. The helper is a review aid, not an isolation boundary.
5. Integration lead reads the patch and verifies the relevant invariants. Independent review is required for tenancy/auth, document release, migrations, signatures/money, secrets and external actions. It is not necessary to summon every role for text changes.
6. Update registers, verify current evidence, checkpoint, commit, push and read back the actual remote branch when available. Open/update the task issue and draft PR under the existing instruction. Do not merge unreviewed sensitive changes or deploy production merely to complete a checklist. Continue other ready work while a specific external step is blocked.

## Context and failure controls
A fresh conversation starts with root AGENTS.md, BUILD_STATE.json, generated RESUME.md and `os:status`, then only the selected task's sources. A checkpoint states unfinished files, evidence freshness, decision assumptions and first incomplete action. Commit unfinished work to a clearly labeled WIP feature branch when necessary; never call it accepted. Do not compress unresolved contradictions into certainty.
If the agent cannot confidently identify source, current task or next action, inspect the registers and Git state, reconcile the inconsistency, and checkpoint. If the same failure repeats without new evidence, stop that retry loop, preserve the first failure/log and change the diagnostic approach. Do not rerun until green or silently skip a required test. No promise of unattended continuation when the session is closed.

## Efficient evidence
`npm run os:verify -- PROFILE` records exact argv, exit status, source hashes, profile, Node/platform/environment identity, log checksum and observed HEAD. A matching pass is reused; changed covered files, new files under an input directory, changed tests/config/profile/environment, or altered logs invalidate it. Common environment variables are hashed, never stored in clear text; additional relevant variables must be listed in profile.environment_variables. The profile input list must include every dependency of the claim and be reviewed when architecture changes. This is tamper-evident change tracking within a trusted repo, not a cryptographic attestation against a malicious committer.
Static contract tests prove only static constraints. Runtime auth and document tests must use authentic identities and bypass UI hiding; browser tests prove representative journeys. Production/real service evidence needs the actual deployed revision, migration set, configuration, environment and fixture identity and should not be cached across mutable environments. Use `--force` for an explicit required revalidation, with reason recorded in the task. Avoid duplicate test matrices at every layer.

## Checkpoints and Git
`npm run os:checkpoint` observes local Git and writes SESSION_CHECKPOINT.json/RESUME.md. `npm run os:checkpoint -- --verify-remote` additionally checks the named branch on the exact Auxilium repository. It never pushes. A matching remote HEAD covers that commit only, not an uncommitted checkpoint or other local changes. After updating and committing the checkpoint, push and verify the new HEAD using `git ls-remote`; record that result in the handoff/PR. Do not chase an impossible self-containing commit hash by repeatedly rewriting the checkpoint.
Keep source, migrations, requirements, decisions, test evidence, meaningful issue/PR descriptions and handoffs in Git. Keep secrets outside Git. Cursor uses the same clone/branch, not an independent source of truth. If GitHub is unavailable, save the reviewable patch/package and explicit pending push; do not claim multi-location persistence.

The importer source and its tests are also preserved in tools/package-importer for Git history. To use that copy, pass --package-root pointing to the extracted continuation package. The package-importer verification profile exercises isolated Git fixtures; it does not import into the live repository or prove a GitHub push.
