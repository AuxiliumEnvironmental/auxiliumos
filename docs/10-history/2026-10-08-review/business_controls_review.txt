AUTHORIZATION INTERPRETATION
The owner's 2026-10-08 instruction authorizes building logically consistent recommended defaults and flagged placeholders without stopping the whole build. Implement and test these recommendations in reversible development configuration. That is permission to develop, not evidence that named business authority, binding commercial terms, scientific qualifications, or real-client release decisions were finally approved. Record Proposed default / Implemented in dev / Owner confirmation pending distinctly. Activation gates block only the affected binding action, never unrelated implementation. Do not keep obsolete documentation-only phase restrictions as a universal build stop.

SETTLED RULES THAT SHOULD NOT BE REOPENED
- Preserve canonical data spine and modular full enterprise destination; first integrated workflow is sequencing, not a reduced product ceiling (Decisions 002, 003, 012).
- Simple client surfaces and detailed internal logic remain separate; client type changes defaults rather than available capabilities (004, 005).
- Messages, uploads and AI output may draft changes but never alter approved scope, caps, sampling, signed agreements or release state (006 and change workflow).
- Classification, exact version, required approval, authorized audience and audit precede client document release (007).
- Human professional/scientific review is distinct from system administration and commercial/signature authority (008, role matrix).
- No PHI in v1; no secrets or real sensitive client records in development prompts/test fixtures; no broad public data policies (009, 010, 014, D-SCHEMA-009/010).
- Latest explicit user direction preserves Moldo as an independent operating application with a controlled OS integration. Moldo-only staff do not gain OS visibility. Companion work is deferred.

OWNER DECISION REGISTER: RECOMMENDATIONS, NOT APPROVALS
Use OD IDs as suggested integration IDs; parent may map them into a final master register. Full original FD/Q IDs should be retained for traceability.

OD-01 | Operating account and portal defaults
Recommendation: support simple project clients and enterprise portfolio/MSA clients on the same canonical OS, using progressive disclosure and module entitlements; ordinary small projects need not manufacture an MSA or portfolio.
Capability: onboarding, client portal, module visibility.
Activation gate: actual account configuration; owner reviews commercial packaging, not every screen or implementation detail.
Sources: Q001/Q013; Decisions 003-005; foundation spine.

OD-02 | Named role assignments and delegation
Recommendation: implement the full proposed role/action catalogue with scoped assignments. Separate staff identity, active membership, scope assignments and delegated actions. System Admin is technical authority, not automatic scope/release/signature authority. One qualified person may hold multiple explicitly assigned roles.
Capability: all permissions and workflows.
Activation gate: owner confirms real staff authority and client representatives; no live role grant inferred from a name/title alone.
Sources: FD-01/02/11/12/13/15/16; Q002/Q003; ROLE_PERMISSION_MATRIX permanent rules.

OD-03 | Document release and separation of duties
Recommendation: final scientific/technical reports always require an assigned qualified Technical Reviewer to approve the exact revision; Document Controller performs the release action. PM/Account Manager reviews routine nontechnical packages; Finance releases invoices; validated signature workflow distributes signed authorization to its authorized parties. Model review and release as separate actions. Allow configurable dual-role operation for routine work only, proposed for the owner's small team; require different people for configured sensitive/high-risk categories.
Capability: reports, lab results, QBRs, legal-sensitive files, invoices.
Activation gate: owner confirms whether the same qualified person can perform both routine actions, the high-risk category policy, and actual designated reviewers/releases. Legal-sensitive release gets designated professional/legal review when applicable; AI cannot supply it.
Sources: FD-03; Q004; DOCUMENT_RELEASE_WORKFLOW Release Authority and Open Decisions; role matrix.

OD-04 | Client visibility and document grants
Recommendation: hybrid access: active membership AND assigned object scope AND permitted document class AND permitted state AND released audience/grant. Explicit narrow grants for restricted/executive documents. Site Champions see released ordinary facility reports within their assigned facility if included in release audience, never finance/executive content by role alone. Client executives get assigned account/program summaries and released executive material, not blanket access to every file. Billing sees invoice/PO/payment context and minimal project identifiers/status, not technical contents.
Capability: client views, storage/downloads, enterprise dashboards.
Activation gate: per-account release audience and role assignments; confirm defaults in owner decision batch before live onboarding.
Sources: FD-04/11/12/13/16; document and role matrices; D-SCHEMA-003.

OD-05 | Uploader receipt and historical documents
Recommendation: allow an authorized uploader to see their own safe submission receipt and submitted file without presenting it as an approved official deliverable; quarantine can override that access. Preserve immutable previously released versions internally. Hide superseded versions from ordinary client lists by default; explicit historical access is separately authorized and clearly marked Superseded. Withdrawal immediately removes current access and creates follow-up task/notice but cannot retract already downloaded copies.
Capability: client uploads, version history, withdrawal.
Activation gate: owner confirms historical-client policy and notification wording; explicit grants control deviations.
Sources: DOCUMENT_ACCESS_MATRIX Client Upload/Supersession/Open Decisions; DOCUMENT_RELEASE_WORKFLOW.

OD-06 | Scope, sampling and scientific authority
Recommendation: PM prepares scope; designated qualified reviewer approves technical content. Human review for all enumerated high-risk categories and new/unapproved templates. Low-risk repeat work may use a previously approved template only within unchanged boundaries. Client Project Approver can accept scope/decline recommendations only within explicit delegation; Agreement Signer remains separately assigned. A sampling declination records decision and limitations, never manufactures sampling-supported conclusions. AI may draft limitations for human review.
Capability: intake, scoping, sampling, report statements.
Activation gate: owner confirms approved template catalogue, review exceptions and delegate limits; qualified humans still sign actual professional conclusions.
Sources: FD-05/10; Q005/Q014; REQUEST_STATE_MACHINE review gates; CHANGE_AUTHORIZATION_WORKFLOW.

OD-07 | Rates, caps, deposits, changes and expiration
Recommendation: versioned account/program rate cards and approval delegations. No automatic nonzero spending authority or invented live prices. Missing cap/delegation means pending authorization. PM drafts changes, technical and finance reviewers review their impacts, and delegated client approver accepts. Sampling within an expressly approved plan/budget can proceed; changed method, quantity beyond authorization, cost, purpose or deliverable triggers review/change flow. Example numbers in fixtures must be labeled synthetic. Build configurable ROM/change expiration rather than hardcoding an unapproved time window.
Capability: ROM, finance, agreements, scheduling release, change control.
Activation gate: real rate cards, payment terms, thresholds, validity periods and authorized client signers must be recorded before binding use.
Sources: FD-06/08; Q006; request, change and emergency workflows.

OD-08 | MSA scope and preauthorization
Recommendation: classify work as included, rate-card billable, service authorization required, change required, vendor/specialist, out of scope, or emergency using the actual versioned program terms. Receipt may auto-enter triage; it never silently accepts work or promises mobilization. Program coverage and active facility entitlement must be explicit.
Capability: programs/MSAs, enterprise intake, recurring service delivery.
Activation gate: actual executed MSA and approved structured translation of its terms; no inferred unlimited-service commitment.
Sources: Q009; REQUEST_STATE_MACHINE permanent rules; EMERGENCY_EXCEPTION_WORKFLOW.

OD-09 | Emergency response authority
Recommendation: assigned Site Champions may send urgent P1 alerts; human triage owns response. P0 shows external emergency/facility protocol guidance and does not promise Auxilium first response. Mobilization requires a configured valid MSA clause, signed emergency authorization or explicit limited conditional approval. No generic automatic emergency cap; absence is pending authorization. Preserve safety review and limited scope and generate follow-up scope/authorization work.
Capability: emergency routing, response, after-hours scheduling.
Activation gate: named on-call senior approver, client delegates, scope/cap/duration thresholds, after-hours terms, contact/escalation plan and any pre-signature exception.
Sources: FD-07/08; EMERGENCY_EXCEPTION_WORKFLOW.

OD-10 | Professional qualification and geographic eligibility
Recommendation: services/templates reference required competencies, credentials, jurisdiction and reviewer assignment. Unknown/expired eligibility is review-required, never silently accepted. Engineering, medical, legal/coverage and licensed specialty work route to a qualified human/vendor rather than being represented as an Auxilium capability by generated copy. Do not translate certifications into unlimited practice authority.
Capability: service catalogue, assignment, scoping, reports, vendor referral.
Activation gate: designated qualified person confirms real service/jurisdiction boundaries and client-facing promises; owner approves commercial offerings.
Sources: FD-10; Q014; role matrix; request/change/emergency gates.

Sequence its UI after foundation; do not permanently remove it because the first slice excludes vendor tables. Distinguish referral, client-direct vendor and Auxilium-managed vendor arrangements in configuration.
Capability: vendors, work orders, credentials, costs.
Activation gate: owner confirms actual contracting relationship, credential requirements and allowed access for each vendor/program.
Sources: FD-14; vendor role/document rules; full module vision.

OD-12 | Audit and retention

Record authorization and exact document version on changes/releases. Preserve history and disable automated permanent destruction until retention rules are approved. Legal hold preservation is a separate control from access restriction; do not use one ambiguous flag for both.
Capability: audit, record retention, archives, export/discovery support.
Activation gate: retention schedule and hold/restriction authorities confirmed before automated deletion or client audit export.
Sources: FD-17; D-SCHEMA-005; document workflow; RLS audit protection.

SOURCE CONTRADICTIONS AND IMPLEMENTATION GAPS
1. SCHEMA_REGISTRY top says no migration/schema; bottom records Issue #80 migration and seed artifacts. AGENTS/CURRENT_HANDOFF/OPEN_QUESTIONS still point to creating the migration. Do not repeat Issue #80. Application to any database remains unverified.
2. SEED_DATA_REGISTRY says future-only/no seed files although foundation_demo_seed.sql exists. Fix current status while preserving historical context.
3. Q008 remains Founder decision needed despite approved no-PHI Decision 014 and confirmed D-SCHEMA-009. Current v1 prohibition is settled.
4. Original founder checkpoint says no schema/auth/RLS/storage work; user now authorizes reversible implementation of recommended defaults. Explicitly supersede the execution phase instead of leaving contradictory active prohibitions or claiming all business policies approved.
5. Role matrix assigns draft role permissions but labels everything not implementation-approved; dev-schema allowed role list is only a subset. The full role model must not be accidentally replaced by the seed subset.
6. removed_suspended is encoded as a role_key in current SQL. That cannot alone reliably express disablement when the same user has other role rows. Add independent user/membership lifecycle and deny precedence in a future migration and tests.
7. AGREEMENT_AUTHORIZATION_WORKFLOW, PROJECT_STATE_MACHINE and SCOPE_STATE_MACHINE are three-line placeholders. Detailed request/change/emergency/document plans do not constitute completed transition specifications for those objects.
8. Request/document states in current SQL accept any nonblank text. No release approval, immutable version, document grant, storage or auth FK implementation exists. Migration tests do not establish runtime permissions/workflow integrity.
9. incident_requests combines Incident and Project Request for the foundation prototype; original spine treats these as distinct concepts. Explicitly design/refine their relation before the final operating system depends on them. Do not silently perpetuate a one-incident/one-request assumption.
10. Account-scoped system_admin in seed design is not the final global admin model. Account membership alone is expressly insufficient for facility and document permissions.
11. Documents carry both is_internal_only and free-text release_state; future invariants must prevent contradictory states from granting access. Archive/Superseded appears as a document class and state, while version history needs its own unambiguous representation.
12. Supersession flow currently marks old version superseded on creation of a new version; refine so creating a draft replacement does not inadvertently remove the still-current released version. Release approval must bind to the exact new revision.
13. Download rule treats 'blocked by legal hold' as possible denial; preservation hold and restricted access are distinct policy controls. Clarify without inventing legal obligations.
14. Audit immutability and download/view audits are intended but not implemented. A signed URL issuance event is not proof that a human downloaded/read the file; record accurate event semantics.
15. Many documents conflate readiness approval, release action, role label and real human authority. Preserve separate concepts and audit them separately, even when one qualified person holds multiple roles.
16. Moldo appears nowhere in this repo snapshot. Its current independent-integration direction must be recorded as new, not described as already implemented or historically approved in these files.

TEST FOCUS WITHOUT REDUNDANCY
Critical tests should establish actual allowed and denied behavior: wrong account, unassigned facility, inactive/suspended membership despite other roles, malicious role grant, direct object URL, unreleased/internal/restricted document, exact-version approval, scope change without authorization, stale/replayed integration event, duplicate event, revocation, and audit event creation. SQL text contract checks remain useful only for their narrow purpose. Run targeted tests for affected code and dependent invariants, integration gates for shared changes, and full release gates when a candidate is promoted. Reuse evidence only for the same commit/config/data conditions or with documented unaffected dependencies; do not call untested cloud/live behavior verified.
