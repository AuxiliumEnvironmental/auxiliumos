MINIMAL DURABLE CONTROL CONTRACTS
Use a small number of canonical JSON files plus human-readable concise handoff, not 20 mutually mirrored status docs. Suggested contracts (can combine if implementation simpler):
- workplan.json: task id, parent milestone, requirement IDs, status enum (planned/ready/in_progress/implemented/verified/blocked/done), dependency IDs, assigned owner, branch, allowed path globs, source refs, acceptance IDs, decision IDs, risk tier, evidence IDs, blocker, next action. Distinguish done code from deployed or user-accepted.
- evidence.jsonl or per-task evidence JSON: ID, task ID, exact command, exit code, UTC, evidence level (static contract/runtime DB/API/browser/manual), source tree/commit hash, test file hash, relevant dependency manifest+config hashes, environment ID safe label/version, result/log path+sha256. A pass alone without source/env identity is not reusable. Do not fabricate tool runs; skipped/unavailable != pass.
- checkpoint.json: version, source baseline and observed working tree, active tasks + branches/worktrees, last completed task, first incomplete action, pending blockers, owner decisions, short next command, persistence (local_commit, remote_commit/null, push state, durable package identity). Don't self-reference a commit that contains its own checkpoint; use base commit plus tree/content digest or latest applied commit from git at resume.
- decisions.json: ID, issue, recommendation/rationale, status proposed/implemented_provisional/approved/rejected/superseded, reversible code/config path, affected requirements/tasks, activation conditions, approved_by/date/evidence nullable. Professional sign-off remains a human action; unspecified real financial defaults cannot be invented as approved authority.
- source-manifest.json: path/title, origin and date, SHA256/version, read status, authoritative/historical status, exact evidence or access gap. Useful for initial comprehensive audit and later changed-input detection; no need reread everything each task.

ANTI-DRIFT AND PARALLELISM
- One integration lead owns current state, task registry, dependency graph, schema/API contracts and shared lockfiles. Nine roles can be responsibilities rather than nine continuously running agents.
- Separate branches/worktrees for concurrent writers; exclusive file ownership for shared migrations, schema registries, auth policies and package locks. Agents writing shared docs return a patch or note to lead. No simultaneous edits to same shared directory assumed isolated.
- Start workers with bounded task, pinned source, relevant docs only, explicit input/output contract and stopping condition; do not fork entire long chat by default.
- Lead compares actual changed files to allowlist and merges/reviews code, not agent claims. Worker final includes diff, tests/evidence and unresolved decisions.
- Cold resume: inspect git branch/head/status; read compact handoff/workplan; compare source/evidence hashes; check remote reachability/persistence; choose first uncompleted ready task; continue under existing authorization. Do not rerun completed tests merely because chat changed.
- Checkpoint at logical completed changes and before tool/chat handoff, not every minute. Save incomplete work transparently in WIP branch if time/context interruption; never imply acceptance.
- No unseen background continuation promise. Context-limit trigger means commit/checkpoint and give short resume prompt, not force giant conversation indefinitely.
- Historical chats help reconstruct requirements but never outrank verified present source or latest explicit user instructions. Missing/private conversations marked unavailable.

EFFICIENT TEST POLICY
- Map tests to consequential requirements and changed dependencies. Rerun only invalidated evidence during development, then required integration gate at merge/release.
- Permission/state/document controls: real local database/API denial tests under authentic users, bypassing UI; browser verifies representative end-to-end paths and phone usability. Static SQL-text tests are not RLS runtime proofs.
- Test changes in implementation without just mirroring implementation logic. Explicit outcomes: unauthorized account/facility, revoked user with existing session, stale revision release, guessing storage keys, cross-account foreign keys, incorrect stage or role, repeat requests and retries, partial failures/audit omissions.
- Reuse evidence only when code/test/config/dependency/environment relevant to claim are unchanged. Docs-only copy change need not rerun database matrix; auth change invalidates all dependent authorization evidence.
- Avoid flaky re-run-until-green. Capture first failure, classify cause, fix and rerun scoped test. Failures must be visible and not converted to skips.

BASELINE-AWARE PACKAGE IMPORTER RECOMMENDATION
- Deliver original baseline identity + overlay and SHA256 manifest; never tell user to replace whole live repo with ZIP.
- Validate clean git working tree and intended remote; don't require branch literally named main, don't discard unrelated local work, don't force push.
- Read all intended target file states first. Old baseline hash means safe update; already new hash means no-op; missing new-only file means safe addition; any divergent hash/addition collision means conflict report and NO partial mutation.
- Reject unsafe paths, absolute paths, '..', symlinks and archive traversal; no surprise deletes or executable downloads. Imported package should preserve current non-target source.
- Optional ancestor check using archive commit if present, but archive commit alone does not guarantee remote still current. New unrelated source may require reconciliation before claiming package status current.
- Provide dry run with exact add/update/already/conflict counts, then intentional apply; no need ask approval repeatedly since user authorized. Transactional staging/backups or git diff recoverability; rerun importer should be idempotent.
- Commit onto new branch, run meaningful control/importer tests, review diff, push/PR if access available. GitHub blocked => local package/persistence explicitly pending, not complete.

MEANINGFUL VALIDATIONS FOR THE MODERNIZATION ITSELF
1. Golden path importer applies overlay; second application makes no change.
2. Modify existing target => whole import rejects and no target mutates.
3. New-file collision, dirty working tree, unsafe path, symlink => rejected without destructive action.
4. In-memory invalid task dependencies/cycle or done task with absent evidence => validator fails.
5. Edit code/test/config covered by passing evidence => evidence stale, affected task/release not verified.
6. A child claim of completion with files outside allocation => lead rejects integration.
7. Cold-start audit can name correct first remaining task and source without reading old chats.
8. Check active rule files don't retain contradicting stage-only stop gates; historical docs clearly labeled and linked to current mandate.
